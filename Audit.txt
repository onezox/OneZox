================================================================================
ONEZOX ENGINE — POST-M2 CODEBASE AUDIT
================================================================================
Scope: full read-only audit of the OneZox engine as it stands after Phase-05
(MILESTONE M2 — Safe Model Ops), conducted against the actual files on disk and
the live onezox-dev cluster, not against the completion records' account of what
was built.

Method: every finding below was verified by reading the file or querying the
cluster at audit time. One temporary read-only probe pod was created and deleted;
nothing was mutated. Credential values are redacted throughout — where a
credential had to be checked, only its lookup RESULT is recorded, never the value
or its hash.

Sections:
  1. ACTIVE BUGS AND UNRESOLVED ISSUES
  2. KNOWN ISSUES, DEFERRALS, AND TRACKED ITEMS
  3. RECOMMENDATIONS AND HARDENING

SECTION 1: ACTIVE BUGS AND UNRESOLVED ISSUES
================================================================================

--------------------------------------------------------------------------------
S1-1  [CRITICAL]  Datastores have no network policy, and two services connect to
                  CockroachDB as root. This defeats EC3 and EC4 outside the
                  narrow paths they were proven on.
--------------------------------------------------------------------------------
WHAT IS BROKEN — three facts that compose into one exposure:

  1. root is a superuser and bypasses all GRANT/REVOKE:
       rolname,rolsuper
       root,t        admin_api,f        control_plane,f

  2. Two services connect as root:
       services/edge-gateway/src/auth/store.rs:18
         cfg.user = Some("root".to_string());
       services/data-plane/main.py:567
         host=pg_host, port=26257, user="root", database="defaultdb", ssl=False,

  3. NO CiliumNetworkPolicy exists for any datastore. The 7 policies in the
     cluster cover application services only. CockroachDB, etcd, Vault, Redis and
     MinIO have none — so they are not default-deny, they are default-ALLOW.
     (Cilium only switches an endpoint to default-deny once a policy selects it.)

REPRODUCTION (run during this audit, read-only). An unlabeled pod in the default
namespace, with no credentials and no mesh identity:

    connected_as,is_superuser
    root,t
    model_active_rows_readable   5
    audit_rows_readable          24

TCP reachability from that same pod:

    etcd:2379             OPEN
    vault:8200            OPEN
    redis:6379            OPEN
    control-plane:50051   BLOCKED (timeout)   <-- positive control

The control-plane result is the positive control: services WITH a policy are
genuinely protected, which is what proves the datastore results are an absence of
policy rather than a broken test.

WHY THIS MATTERS. Superuser read implies superuser write. Any pod in the default
namespace can therefore UPDATE model_active — changing the live model pointer
outside signed manifests and rollout — and UPDATE/DELETE audit_log. etcd being
open is a second, independent bypass: /onezox/active/{model_ref} lives there, so
writing it directly changes what data-plane resolves without touching the
database at all.

RELATION TO THE EXISTING PROOFS. Phase-05 Step T's proofs are not wrong. They
tested admin_api's DB role, and network access TO control-plane, and both hold
exactly as recorded. But EC3's "audit_log is immutable" and EC4's "no path exists
to mutate a live model outside signed manifests + rollout" were stated generally,
and generally they do not hold. The proofs were scoped narrower than the claims
they were taken to establish.

SEVERITY: blocks the security claims (not the functionality).

SUGGESTED FIX:
  (a) Create edge_gateway and data_plane DB roles with real least-privilege
      grants; change both connection strings off root.
  (b) Add CiliumNetworkPolicies for crdb / etcd / vault / redis / minio,
      allowing only the services that legitimately need each.
  (c) Re-run Step T's DB-layer probe as each non-root role, and add a direct
      etcd-write attempt to the EC4 proof set.

S1-2  [CRITICAL]  CI runs zero tests.
--------------------------------------------------------------------------------
.github/workflows/ci.yml is 159 lines and contains exactly two jobs:

    JOB: proto        (buf lint + buf breaking)
    JOB: build-sign   (docker build, SBOM, sigstore signing)

Grep across the whole file for `go test|cargo test|pytest|npm test|tsc` returns
ZERO matches.

The ~155 tests that back the M2 exit criteria — 49 admin-api, 45 control-plane,
61 data-plane, plus edge-gateway's Rust suite — run only when invoked by hand. A
regression in the RBAC allow-list, the rollout state machine, the audit fail-loud
path, or the canary weighting would pass CI silently.

HOW TO OBSERVE: open .github/workflows/ci.yml; there is no test job.

SEVERITY: blocks confidence in every future change. This is a process defect, not
a code defect, but its blast radius is every EC proven so far.

SUGGESTED FIX: add a `test` job with a per-language matrix (go/cargo/pytest/tsc);
make build-sign depend on it.

S1-4  [HIGH]  A real tenant API key sits in a tracked file, via a mechanism that
              will keep re-adding them.
--------------------------------------------------------------------------------
.claude/settings.json:274 contains a Claude Code permission-allowlist entry that
records a full curl command INCLUDING its Authorization: Bearer oz_test_<...>
header.

VERIFIED (without printing the value or its hash): lookup against api_keys
returned found,active = 1,0 — the key is REAL (present in the table) and ALREADY
REVOKED, so it is not currently exploitable against this cluster.

The structural problem is worse than this one key:
  - .claude/settings.json IS tracked (committed at b606aef, Phase-00).
  - .gitignore covers .claude/settings.local.json but NOT settings.json.
  - HEAD's committed version is clean; the key exists in the WORKING TREE only.
    It has stayed uncommitted purely because every commit in this build used
    explicit paths — it is one `git commit -a` away from permanent history.
  - The allowlist grows automatically on every approved
    `curl ... -H 'Authorization: Bearer ...'`, so this recurs BY DESIGN.

This is the FOURTH credential exposure in this build, and the first that persists
on disk rather than only in a transcript. (Prior three: P04 base64 secret dump,
P04 IssueProviderToken response, P05 Set-Cookie header.)

SEVERITY: high — currently contained, structurally recurring.

SUGGESTED FIX: add .claude/settings.json to .gitignore and `git rm --cached` it,
or strip credential-bearing entries plus add a pre-commit hook.

S1-5  [HIGH]  edge-gateway's Docker build has no lockfile — builds are not
              reproducible.
--------------------------------------------------------------------------------
services/edge-gateway/Dockerfile:12

    COPY Cargo.toml Cargo.lock* ./

`ls services/edge-gateway/` returns: Cargo.toml  Dockerfile  src — there is NO
Cargo.lock. The lockfile is at the repo root (workspace-level, tracked), but the
build context is services/edge-gateway (.github/workflows/ci.yml:87). The `*`
glob therefore matches nothing and the build silently proceeds WITHOUT a lockfile.

Every dependency in services/edge-gateway/Cargo.toml is a caret range
(axum = "0.8", tokio = "1", serde = "1", sha2 = "0.10", ...), so any rebuild can
resolve different transitive crate versions than the ones tested and deployed.

Notably edge-gateway is the lone exception: the four Go services ship go.sum and
admin-panel ships package-lock.json, all correctly copied.

SEVERITY: silent correctness / supply-chain risk. No current misbehavior, but a
rebuild months from now is not guaranteed to produce the audited binary.

SUGGESTED FIX: build from repo root with `-f services/edge-gateway/Dockerfile .`,
or commit a service-local Cargo.lock.

S1-6  [MEDIUM]  A manifest that fails signature verification is never re-verified
                until an etcd event or a process restart.
--------------------------------------------------------------------------------
services/data-plane/model_registry/__init__.py:266-308

watch_forever re-syncs on WATCH failure only (the except branch at lines
300-308). Verification failures do not raise — they mark the manifest untrusted,
and sync_once still reports success. With etcd healthy there are no new events,
so nothing ever re-verifies.

This is precisely the failure observed live during Phase-05 Step P: data-plane
logged `signature verification FAILED, refusing to trust` for all six openai
manifests, then `initial sync complete`, and served model_not_found until a
manual `kubectl rollout restart`.

ASYMMETRY WORTH NOTING: services/edge-gateway/src/main.rs:179 uses
`.expect("model_registry: initial sync failed")`, which panics -> crash-loop ->
Kubernetes restarts it -> it self-recovers once Vault returns. The Rust service
accidentally has BETTER recovery behavior than the Python one.

This is the concrete mechanism behind the tracked boot-retry gap (S2, item 4) —
recorded here as a bug because "sticky verification failure" is more specific and
more actionable than "no retry at boot".

SEVERITY: silent correctness — the service looks healthy (readyz passes, boot
completes) while serving nothing.

SUGGESTED FIX: a periodic re-sync timer, or backoff re-verification of entries
currently marked untrusted.

S1-7  [MEDIUM]  edge-gateway's canary resolve() is dead code — the Step K
                "both languages" parity is unexercised.
--------------------------------------------------------------------------------
cargo clippy on hand-written code:

    method `resolve` is never used         --> src/model_registry.rs:357
    function `pick_version` is never used  --> src/model_registry.rs:108
    enum `ManifestError` is never used     --> src/model_registry.rs:57

The cache IS synced and Vault-verified (main.rs:179-184: blocking sync_once at
boot plus a spawned watch_forever), but its ONLY consumer is list_active() for
GET /v1/models (ingress.rs:243-248). Version resolution happens in data-plane.

Phase-05 Step K implemented canary-weighted resolve() in BOTH languages with unit
tests in both. The Rust tests pass, but they exercise a path that never runs in
production. Consequences: false assurance about canary parity, and a future change
to canary semantics must be made in two places, one of which no live proof can
validate.

SEVERITY: silent correctness (misleading test signal), not incorrect behavior.

SUGGESTED FIX: delete the Rust resolve()/pick_version()/ManifestError and their
tests, OR mark with #[allow(dead_code)] plus a comment stating it is staged for
future use. Do not leave it silently dead.

NOT FINDINGS, checked and cleared in the same pass:
  - pb_generated/gateway.v1.rs "never constructed" warnings are generated
    protobuf types. Normal.
  - normalize_embeddings being dead is CONSISTENT with /v1/embeddings honestly
    returning HTTP 501 via not_wired() (ingress.rs:113-126). Correct behavior.

================================================================================
OVERALL ASSESSMENT
================================================================================
Application code quality is high, and the completion records are accurate about
what they claim — every exit-criteria proof re-tested during this audit
reproduced exactly as recorded.

The dominant risk is not in the application logic but in the LAYER BENEATH IT.
The datastores were never brought into the security model that the services were:
they hold the state that EC3 and EC4 are about, and they are reachable by any pod
with superuser credentials. Separately, CI never enforced the tests that back the
milestone.

Both are inexpensive to fix now and materially more expensive after Phase-06 and
Phase-07 build on top of the current foundation.
