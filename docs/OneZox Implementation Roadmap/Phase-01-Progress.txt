2026-07-28 — Redis Cluster / stub drift discovered during Phase-01 Step A
--------------------------------------------------------------------------------
FINDING: Phase-00's "verified" state had drifted by the time Phase-01 work
began. Redis Cluster reported cluster_state:fail (`cluster info` on
redis-cluster-0), and all three Phase-00 stubs (edge-stub, dataplane-stub,
provider-stub) were in CrashLoopBackOff with restart counts in the 140-175
range, ages ~44-45h. This was NOT caused by any Phase-01 change — it was
discovered while verifying dataplane-stub's new Submit gRPC shim (Step A6),
before that step's own code had even been redeployed.

ROOT CAUSE: the onezox-dev kind cluster's Docker containers had been through
a WSL2/host restart. Per the existing restart guide
(Phase-01-Local-Restart-Guide.txt), the 3 kind node containers came back up
fine and all pods reached Running — but Redis Cluster's 6 pods run on
emptyDir (intentionally ephemeral, no PVC). Their on-disk cluster gossip
state (nodes.conf) survived the container restart, but each pod's IP address
did not — freshly assigned by the CNI on every pod (re)start. The result:
every node's gossiped view of the cluster referenced IPs no other node was
actually listening on anymore. `cluster nodes` confirmed this directly:
gossiped IPs (e.g. 10.244.1.190) did not match any current `kubectl get pods
-o wide` IP (e.g. 10.244.1.42) for the same node ID. The three stubs then
failed their own boot sequences at the Redis set/get step (edge-stub panicked
outright; provider-stub and dataplane-stub errored/hung), which is why they
were crash-looping — a symptom of the same root cause, not a separate bug.

FIX APPLIED: `kubectl delete pod -l app=redis-cluster` (StatefulSet
recreated all 6 with clean emptyDir state), waited for all 6 Running, then
re-ran the cluster bootstrap by deleting and reapplying the existing
`redis-cluster-init` Job (platform/operators/redis/redis-cluster-init-job.yaml,
unchanged) — `cluster_state:ok` confirmed afterward, 16384/16384 slots
covered. edge-stub and provider-stub were then pod-deleted (Deployment
recreated them) to force them off their stale in-memory cluster topology;
both came up Running immediately once Redis was healthy. No manifest files
changed for this fix — see finding #2 below for how it was applied.

PROCESS LESSON: a completion record (Phase-00-Complete.txt) documents
verification AT THAT POINT IN TIME, not an ongoing guarantee. Emptydir-backed,
intentionally-ephemeral components (Redis here; see Dependencies.txt section
6, "rebuild-on-demand, no DR needed") are exactly the ones most likely to
silently drift across a host restart, because kubelet/the Deployment
controller will happily report every pod "Running" while the cluster-level
protocol above it is broken. The restart guide already has the right checks
for this (Phase-01-Local-Restart-Guide.txt section 3.2 `kubectl get pods -A`
and 3.5 `redis-cli cluster info`) — the gap was that they were not actually
re-run at the start of this work session before starting Phase-01 changes,
so the drift wasn't caught until it blocked Step A6 mid-build.

ACTION ITEM (standing practice going forward): at the start of every Phase-01
work session, before writing or deploying any code, run a minimal liveness
check first: `kubectl get pods -A` (look for anything not Running/Completed)
and `kubectl exec -n default redis-cluster-0 -- redis-cli cluster info | grep
cluster_state` (expect cluster_state:ok). This is cheap, catches this exact
failure mode immediately, and avoids re-discovering environment drift in the
middle of an unrelated step.

2026-07-28 — redis-cluster-init Job recovery applied outside Argo CD
--------------------------------------------------------------------------------
FINDING: the fix above (`kubectl delete pod` on the 6 redis-cluster pods,
then `kubectl delete job` + `kubectl apply -f
platform/operators/redis/redis-cluster-init-job.yaml`) was applied directly
against the cluster, not through the "onezox-stubs" Argo CD Application.
This does NOT violate the project's GitOps hard rule as currently scoped:
that rule (CLAUDE.md, and Phase-00-Complete.txt's own account of how Redis
was originally provisioned) only covers stub/service and CiliumNetworkPolicy
manifests under platform/stubs/, which is the only path the "onezox-stubs"
Application watches (platform/argocd/applications/onezox-stubs.yaml). Redis
lives under platform/operators/redis/ and was hand-applied directly in
Phase-00 too — this fix used the same, already-established mechanism.

FLAG: this is a known, currently-accepted gap, not a mistake to silently
paper over. Two distinct things are worth keeping separate:
  1. By design, infra operators (Redis, CockroachDB Operator, MinIO, the
     observability stack) are declared-in-Terraform / hand-applied, not
     GitOps-owned — that's an existing, intentional Phase-00 decision, not
     new.
  2. What IS new here: there is no written recovery procedure anywhere in
     the docs for "Redis Cluster gossip state references stale IPs after a
     node restart." A fresh engineer following Phase-00.txt,
     Phase-00-Complete.txt, and Phase-01-Local-Restart-Guide.txt alone would
     hit the exact same cluster_state:fail wall this session did, and have
     no documented next step — only the restart guide's "expect
     cluster_state:ok" with no remediation if it isn't. That is a partial
     gap against Phase-00 exit criterion #1 ("A fresh engineer can clone,
     build, and deploy the cell from docs alone.") specifically for the
     failure-recovery path, not the initial-provisioning path (which is
     documented and was not itself in question here).

This entry is that missing documentation for now. Whether to promote it into
a proper remediation step in Phase-01-Local-Restart-Guide.txt (or a new
troubleshooting doc) is a decision for whoever next revisits that guide —
not made here.

2026-07-28 — Step J (EC4) findings: span tree, metrics, and a Loki gap that
was real but not what it first looked like
--------------------------------------------------------------------------------
FINDING 1 (fixed): before Step J, edge-gateway's OTel span tree was a single
span (edge_gateway.request) with no children — auth, ratelimit, and admission
all ran and completed before the request span was even created (it used to be
created at "meter start," well after admission and normalize). Fixed by
moving root-span creation into pipeline.rs's `Admitted` extractor, as early as
possible (before auth runs), and giving every stage (auth, ratelimit,
admission, normalize, submit, relay) its own explicit `parent: &root_span`
child span. Live-verified in Tempo, twice (before and after Step J's later
/metrics rebuild, to rule out the second rebuild regressing it): exactly 7
spans per real request, no orphans. "Meter" is not a distinct child span —
it's represented by the token/cost/finish_reason fields recorded onto the
root span itself, since Phase-01 has no real usage yet to justify a span of
its own for it.

FINDING 2 (fixed): edge-gateway had no /metrics endpoint at all — flagged as
a known gap back in Step F3b's own comment in
platform/operators/prometheus/prometheus-values.yaml, deferred to this step
on purpose. Added real (not placeholder) request-count, latency-histogram,
and inflight-gauge metrics; the inflight gauge deliberately reuses
admission::AdmissionGuard's existing Redis-backed lifecycle (already verified
correct by Steps H3/I) instead of a second, independent counter. First
attempt rendered as Prometheus *summaries* (client-side quantiles) rather
than true histograms — a metrics-exporter-prometheus default when no bucket
boundaries are configured — corrected with explicit `set_buckets()`. Live-
verified: Prometheus's own TSDB values exactly match real requests made, and
the inflight gauge visibly rose 0->5->8 under 8 concurrent streamed requests
and drained back to 0, not a static reading.

FINDING 3 (fixed, and a process note): edge-gateway had no structured log
line anywhere on the successful-request path — only `tracing::warn!` on
error branches, plus main.rs's one boot line. A real, successful request
produced zero Loki log lines. Fixed with one `tracing::info!` at request
completion in stream.rs's relay() (after the SSE stream fully drains),
carrying request_id and finish_reason explicitly rather than relying on the
JSON formatter's span-field embedding.

While verifying the fix, an initial ~45s poll against Loki found nothing,
which triggered a deeper investigation (per the same "prove the query path
first" discipline as Step H1's raw-key test) into whether promtail itself was
broken: `kubectl get pods -n default -l app=promtail` initially returned
nothing (wrong label — the DaemonSet is separately queryable, pods aren't
labeled `app=promtail`), and two of the three promtail pods
(promtail-hrb4z on onezox-dev-control-plane, promtail-pbwkc on
onezox-dev-worker2) turned out to have genuinely stale logs (nothing since
~12:06 and ~13:15 respectively, vs. current time ~21:00) — consistent with
this session's already-documented pattern of WSL2-restart drift silently
breaking pods that still report Running. This did NOT block edge-gateway's
own telemetry: edge-gateway runs on onezox-dev-worker, served by
promtail-hz29h specifically, which was healthy and actively pushing to
loki-gateway (confirmed via loki-gateway's own access log showing continuous
204s). The actual reason the first poll came back empty was ordinary Loki
ingestion lag relative to how short that poll window was, not a broken
pipeline — a longer wait (60s) and a wide query window found the log line
immediately after. Left promtail-hrb4z/-pbwkc's staleness unaddressed here:
they don't affect any Phase-01 service's telemetry today (nothing Phase-01
cares about runs on the control-plane node; onezox-dev-worker2 hosts no
edge-gateway replica), so fixing them is out of Step J's scope, but it's the
same underlying class of drift as the Redis Cluster finding above and belongs
in the same "known gap" bucket if it starts mattering later.

Net result: EC4 verified complete for one real request across all three
backends — Tempo (7 correctly-parented spans), Prometheus (real request
count/histogram/inflight values), and Loki (one structured completion log
line, request_id and finish_reason present and correct).

2026-07-29 — Redis Cluster drift, third occurrence: now a documented,
one-command recovery
--------------------------------------------------------------------------------
FINDING: a third full host/WSL2 restart produced the identical failure this
session already saw twice (Step A's original finding above; promtail's own
version of the same class of drift noted during Step J): cluster_state:fail,
10923/16384 slots stuck in pfail, all 6 redis-cluster pods still reporting
"Running" throughout. Recovered with the exact same sequence as Step A
(reset the 6 pods, re-run redis-cluster-init), then verified in order:
(1) cluster_state:ok, 16384/16384 slots ok; (2) dataplane-stub and
provider-stub both reached 1/1 Ready — provider-stub needed one pod delete
to force an immediate retry rather than wait out its CrashLoopBackoff timer
against a Redis error that was already stale; confirmed the Step-A6 Submit
shim specifically (not just the pod) by driving one real end-to-end
streamed request through edge-gateway and getting back the shim's actual
canned content; (3) edge-gateway was 1/1 Running the whole time (it
survived the restart) and that same end-to-end request confirms it's
genuinely functional, not just Running; (4) onezox-stubs back to
Synced/Healthy (was Synced/Progressing during the outage).

REMEDIATION (closes the gap Step A's finding above explicitly flagged —
"no written recovery procedure anywhere in the docs"): the manual sequence
is now scripts/recover-redis-cluster.sh — checks cluster_state first and
exits immediately, untouched, if already "ok" (safe to run proactively as
part of the session-start liveness check), otherwise runs the full
reset + reinit + verification sequence, including nudging dataplane-stub/
provider-stub out of a stale CrashLoopBackoff. Referenced directly from
Phase-01-Local-Restart-Guide.txt section 3.5, which previously only said
"expect cluster_state:ok" with nothing to do if it wasn't. Recovery for
this specific, now-predictable failure is one command, not a re-diagnosis,
starting from the next occurrence.

2026-08-01 — recover-redis-cluster.sh fixed Redis but not the dependent
stubs; found the real cause before touching anything, then hardened the
script's own stub-recovery step
--------------------------------------------------------------------------------
FINDING: another WSL2 restart produced the same Redis Cluster drift as
before; scripts/recover-redis-cluster.sh was run and correctly restored
cluster_state:ok, 16384/16384 slots ok. dataplane-stub and provider-stub,
however, were still in CrashLoopBackOff afterward — the first time the
script's own dependent-stub recovery step (added at the end of Phase-01)
did not do its job.

Per explicit instruction, no pod was deleted or restarted before
diagnosing. `kubectl logs <pod> --previous` showed: provider-stub —
an explicit `redis: connection pool: failed to dial after 5 attempts:
dial tcp 10.244.1.154:6379: i/o timeout`, and a direct check confirmed
10.244.1.154 matched none of the current redis-cluster pod IPs (a stale,
pre-reset address); dataplane-stub — no explicit error in its previous
log (it hung silently after "wrote health_probe row"), but `kubectl
describe pod` showed Last State Terminated, Exit Code 137 (SIGKILL), with
Events showing the liveness probe killing it — consistent with a hang on
the same class of stale-connection problem, just without ever logging an
exception before being killed. Both classified as the expected "stale
connection to pre-reset topology" case, not a different root cause (no
MinIO/CockroachDB/config/OOM signal in either).

Before any corrective action was taken, both pods were rechecked and had
already reached 1/1 Running with 0 further restarts — they self-recovered
during the diagnosis window via their own crash-loop backoff cycling,
roughly 2.5 hours after the Redis recovery. No `kubectl delete pod` was
needed or performed. Verified functionally, not just Running: a real
streamed request through edge-gateway returned dataplane-stub's actual
shim content ending finish_reason:"stop", and the "onezox-stubs" Argo
Application was Synced/Healthy.

ROOT CAUSE OF THE RUNBOOK GAP: scripts/recover-redis-cluster.sh's
dependent-stub-recovery step used a kubectl JSONPath boolean-literal
filter (`?(@.status.containerStatuses[0].ready==false)`) to find not-ready
stub pods. This silently matched zero pods against the genuinely
not-ready dataplane-stub/provider-stub — confirmed after the fact, since
both pods still showed multi-day ages at diagnosis time, proving the
script's `kubectl delete pod` never actually fired for them despite the
script completing (Redis's own steps 1-4 succeeded). kubectl's JSONPath
filter engine comparing a raw boolean literal inside a `?()` expression is
a known-fragile pattern.

REMEDIATION: scripts/recover-redis-cluster.sh's Step 5 was rewritten to
emit each pod's raw `ready` value and compare it as a plain string in
bash, sidestepping the JSONPath filter engine entirely rather than
depending on it. Step 6's wait timeout was also widened (90s -> 180s),
since even a freshly recreated pod was observed needing more than one
retry immediately after a Redis recovery, and a clear failure message
(distinguishing "still not the stale-connection case" from a fresh
problem) was added for if the wait times out. Also confirmed the script
itself is idempotent and non-destructive when Redis is already healthy
(re-ran it against the already-recovered cluster: exits at step 1 without
touching anything), and dry-ran the corrected Step 5 logic directly
against the (by then healthy) stub pods to confirm it correctly reports
"already Ready" rather than deleting them unnecessarily.
