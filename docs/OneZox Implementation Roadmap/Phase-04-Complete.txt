--------------------------------------------------------------------------------
PHASE-04 OBJECTIVE
--------------------------------------------------------------------------------
Replace static/inline model config with a real control plane: a model registry
whose entries are signed, versioned, immutable manifests distributed via etcd
and cached independently at edge-gateway and data-plane, plus HashiCorp Vault
as the single home for provider keys, issuing short-lived scoped tokens to
provider-gateway. Mutating a live model config is eliminated as an outage
class. This phase resolves two forward references carried since Phase-02/03:
F9 (Vault-issued provider credentials) and F10 (signed registry manifests
replacing Phase-03's STATIC_MODEL_REF).

DATA-PLANE AND EDGE-GATEWAY: REGISTRY CACHES (STEPS Q, R, S)
--------------------------------------------------------------------------------
Both services independently implement the same shape, in their own language,
never trusting each other's or control-plane's prior verification:

  signed_payload(version_id, model_ref, spec_json) = UTF-8 bytes of
  "{version_id}|{model_ref}|{spec_json}" — byte-identical construction in Go
  (control-plane, signs), Python (data-plane, verifies), and Rust
  (edge-gateway, verifies). spec_json is carried as a plain string at every
  hop (control-plane's envelope struct, Python's dataclass, Rust's serde
  struct) and only json.loads/serde_json-parsed AFTER verification succeeds —
  never re-marshaled before or during what gets hashed, which is what keeps
  it byte-exact across the Go -> etcd -> Python/Rust round trip (the same
  class of bug Step E hit inside CockroachDB's own JSONB column, fixed by
  migration 0013 well before it could recur here).

  Cache.sync_once() / Cache::sync_once(): full get-prefix re-list of
  /onezox/manifests/* and /onezox/active/*, independently signature-verified
  entry by entry before being trusted.

  Cache.watch_forever() / Cache::watch_forever(): on ANY disruption (etcd
  error, stream end, connection failure), the whole loop falls back to a
  fresh sync_once() before re-establishing the watch — this full-re-list
  strategy, not a resume-from-revision-offset strategy, is what makes the
  Step R "missed window" case correct: a manifest that changed while
  disconnected is caught by the next full re-list, not lost to a resumed
  watch that would only see future events.

  A failed verification on an incoming update never evicts or overwrites an
  already-trusted (model_ref, version_id) entry — it only refuses the bad
  update, logs a warning, and keeps serving the last-known-good manifest. A
  verifier call that itself raises/errors (Vault unreachable, etc.) is
  treated identically to a well-formed "no," never allowed to propagate and
  crash the cache (this exact gap crashed data-plane's pod on Step Q's first
  deploy — see PROBLEMS ENCOUNTERED).

  resolve() / list_active() are pure, synchronous, in-memory reads — Python:
  plain dict access; Rust: a std::sync::RwLock read, deliberately not tokio's
  async lock, since there is no I/O on this path. Neither does a per-request
  network call to etcd or Vault, satisfying Phase-04.txt's "off the hot path"
  requirement for the control plane at the two services that actually sit on
  the hot path.

data-plane (Python): vault_client/ (Kubernetes-auth login, Transit verify
  via httpx), model_registry/ (Cache, aetcd-backed). Submit()'s binding logic
  is now `model_ref = request.model or DEFAULT_MODEL_REF` ->
  registry_cache.resolve(model_ref) -> worker_ref, catching ManifestNotFound
  as a clean FAILED_PRECONDITION rather than any crash/hang. 56 pytest tests
  passing (up from 49 at Phase-03's close), including tampered/unsigned/
  garbage-signature rejection, verifier-exception-does-not-crash-sync, and
  last-known-good-survives-a-bad-update — all against a real SHA256-based
  fake verifier, not a stub that always returns true/false. ruff clean
  (generated/ stubs excluded, the existing project-wide convention).

edge-gateway (Rust): vault_client.rs, model_registry.rs (Cache, etcd-client-
  backed via an EtcdReader trait). Introduced #[async_trait] EtcdReader and
  SignatureVerifier traits specifically because etcd_client::Client's own
  methods need &mut self and a live connection, which is untestable by
  direct coupling — mirrors Python's own Protocol-based design. GET
  /v1/models now calls registry_cache.list_active() (Step S), mapped to
  {id, owned_by: "onezox"}, sorted. 60 cargo tests passing (up from ~50 at
  Phase-01/03's close, exact prior count not independently re-verified here),
  2 pre-existing ignored tests unrelated to this phase's work.

PROBLEMS ENCOUNTERED DURING PHASE-04 AND HOW EACH WAS RESOLVED
--------------------------------------------------------------------------------
1. model_manifest.spec_json JSONB reformatting (Step E). CockroachDB's own
   JSONB column type silently re-serializes on write (key order, whitespace),
   which would have broken byte-exact signature verification the moment
   anything re-read and re-hashed it. Caught before it could propagate
   anywhere further; fixed by migration 0013 (spec_json STRING, not JSONB).
   This is the same defect class Phase-03's own architecture already warned
   about implicitly and which this phase had to actively guard against at
   every later hop (etcd round-trip, Python/Rust deserialization) — it did
   not recur, because every later stage was deliberately built to treat
   spec_json as an opaque string until after verification.

2. Data-plane boot crash on a Vault call failure (Step Q, live-caught on
   first deploy). A stray leftover etcd test key from earlier client-library
   evaluation (no signature field) caused sync_once() to attempt a real
   Vault verification at boot; that call failed (data-plane's own Vault role
   didn't exist yet), and the failure propagated as an uncaught exception
   through Cache.sync_once() -> init_model_registry() -> lifespan(),
   crashing the pod into CrashLoopBackOff. Fixed: Cache._verify() now treats
   any verifier-call exception identically to a well-formed "no" — logs a
   warning, returns False, never propagates. The same defensive pattern was
   built into Rust's Cache::verify() from the start and confirmed live when
   edge-gateway was first deployed before its own Vault role existed (it
   logged a warning and kept booting, rather than crashing). Regression
   tests added in both languages.

3. aetcd's watch_prefix() coroutine bug (Step Q, second bug on the same
   deploy). watch_prefix() is itself async def — calling it returns a
   coroutine that must be awaited to get the actual async-iterable Watch
   object; it is not directly iterable on its own. Manifested as a tight,
   silent 2-second retry loop, not a crash, because the surrounding except
   caught the resulting TypeError every time — the watch was never actually
   watching anything. Fixed: `watch = await self._etcd.watch_prefix(...)`
   then `async for event in watch`.

4. Existing etcd watch connections did not notice a Cilium policy change
   (Step R). Applying a surgical ingress-deny CiliumNetworkPolicy on etcd
   did not break already-established long-lived watch streams — confirmed
   via a direct socket test from inside a data-plane pod that NEW
   connections were genuinely blocked while existing ones sat idle,
   unaffected. Resolved by combining the Cilium policy with a forced
   restart of all 3 etcd pods, which broke every existing connection while
   the policy continued blocking only the intended consumers' reconnection
   attempts — this combination is what actually let Step R prove both the
   reconnect and missed-window cases against a genuine disruption.

5. etcd-client's own build.rs needs protoc (Step R). Docker build for
   edge-gateway failed with "Could not find `protoc`" — the etcd-client
   crate compiles its own bundled etcd API .proto files at cargo-build time,
   unrelated to this repo's own committed-proto-stubs convention. Worked
   locally only because the host machine already had protoc installed from
   earlier Go codegen work. Fixed by adding protobuf-compiler to the
   Dockerfile's builder-stage apt-get list, with a comment distinguishing it
   from the repo's own proto convention.

6. A leftover "fake" test manifest inflated the live GET /v1/models count to
   6 (Step T). Not Gemini — Gemini correctly never appeared, satisfying the
   core registry-correctness concern — but a stale test entry from earlier
   Step Q/R/S verification. Removed directly from both etcd and
   CockroachDB, re-confirmed after the watch caught the deletion: exactly 5
   entries, {openai, anthropic, grok, glm, kimi}. Side effect disclosed here:
   data-plane's own DEFAULT_MODEL_REF=fake Deployment env var no longer
   resolves to anything now that "fake" is gone from the registry — a
   Submit request with an empty model field now correctly returns
   FAILED_PRECONDITION/ManifestNotFound instead of silently defaulting to
   provider-fake. This is the expected and desired outcome of "no static
   model config left," not a regression, but is recorded here explicitly
   rather than left to be discovered later.

7. provider-gateway pods with zero registered real-provider adapters after a
   transient cluster-wide DNS blip (Step U, live-caught). All 3
   provider-gateway pods had restarted roughly 79 minutes before Step U's
   own live call, during a DNS/control-plane blip unrelated to this phase's
   own testing (control-plane and data-plane pods show matching-timed
   restarts from the same window). setupCredential's Vault fetch runs once,
   synchronously, at boot only (Step M's own design — see COMPONENTS above);
   it failed for all 5 real providers at that exact boot instant because
   control-plane's DNS name wasn't resolvable yet, and — by design, since
   registration is a boot-time-only action with no later retry-to-register
   path — none of the 5 real adapters were ever registered afterward, even
   though DNS and control-plane were both healthy again within seconds.
   Diagnosed via kubectl logs (a clean "no adapter registered" error, not a
   crash — provider-gateway's own designed failure mode for exactly this
   case) and fixed with a plain `kubectl rollout restart
   deployment/provider-gateway`, confirmed clean re-registration of all 5
   real adapters (only the expected GOOGLE_API_KEY-not-set warning remained)
   before Step U's live call was retried and succeeded. Not a defect
   introduced by this phase's own code — it is an inherent property of
   Step M's boot-time-only registration design, surfaced here because this
   was the first time in the build that a genuinely stale pod happened to
   be sitting in front of a live end-to-end proof. No code change made in
   response: recorded as an operational characteristic worth knowing (a
   provider-gateway pod that boots during a control-plane/DNS outage will
   need a restart once the outage clears, not just time), not tracked as a
   deferral, since fixing it would mean adding retry-to-register logic that
   Phase-04.txt never asked for and which Phase-05's own admin-panel/canary
   work may want to shape deliberately rather than have bolted on here.

8. provider-gateway double-refresh at startup (Step M, live-caught). The
   initial synchronous Resolver.Refresh() and the first iteration of the
   background Run() loop both fired immediately at boot, refreshing every
   credential twice in quick succession. Fixed by carrying the interval
   Refresh() already returned into Run()'s first wait, so the loop waits it
   out instead of refreshing again immediately.

9. A cluster-wide Vault init/unseal script bug (Step B) silently masked a
   raft-join failure — a secondary Vault pod could fail to join the Raft
   cluster and the script would still report success. Fixed before any
   dependent step (C onward) began.
