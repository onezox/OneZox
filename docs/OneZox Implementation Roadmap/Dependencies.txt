================================================================================
ONEZOX IMPLEMENTATION ROADMAP — DEPENDENCIES.TXT
================================================================================
Companion index to Roadmap.txt and Phase-00..Phase-14.
This file does not introduce new build work. It consolidates, in one place:
  1. The phase dependency matrix (who needs whom).
  2. The FORWARD-REFERENCE TRACKER — things DEFINED in one phase but only
     FINALIZED/WIRED in a later phase (with the interim measure to use meanwhile).
  3. Infrastructure provisioning order (which datastore/operator lands when).
  4. Contract (proto/schema) ownership and first-use.
  5. Parallelization rules (what a second team may start early, and the hard
     serialization points).
  6. Datastore readiness map (created vs. production-wired).

This roadmap implements the existing v2 architecture exactly as written; nothing
here redesigns, optimizes, or changes a technology choice. Where a phase file and
this file appear to differ, the phase file is authoritative.

RULE FOR ALL FORWARD REFERENCES:
- The interim measure must never leak into a public contract. Callers see the
  final interface from day one; only the backing implementation swaps.
- A forward reference is NOT closed until the finalizing phase's exit criteria
  pass AND the interim measure is removed (no orphaned durable queue, no lingering
  K8s-secret provider creds, no dual chat writes).

5. PARALLELIZATION RULES
--------------------------------------------------------------------------------
ALLOWED (only if team capacity permits; hard dependencies in section 1 still hold):
- Phase-08 (Chat Service) may start once Phase-03 is GREEN — it does not need the
  deliberate path (06/07). A second team can build it in parallel with 04-07.
- Phase-11 (sandbox + GPU) skeleton may start after Phase-03, BUT its integration
  test requires Phase-07 (multi-agent tool calls) and its retrieval-serving path
  requires Phase-10.
- Datastore operators may be deployed ahead of their "Deploy in" phase (section 3)
  to de-risk, at the cost of idle spend.

FORBIDDEN (hard serialization points — never reorder):
- 04 before 03            (registry needs a running slice to replace static config)
- 06 before 05            (deliberate path needs manifests authored + rolled out)
- 07 before 06            (multi-agent needs IR + scheduler + Temporal)
- 10 before 09            (retrieval complements the Memory Service; Qdrant shared)
- 11 integration before 07 (sandbox isolates real multi-agent tool calls)
- 12 before 06            (replay needs stored IR + recorded outputs)
- 13 before the services it instruments exist (03-12)
- 14 before everything    (multi-region composes all services)

6. DATASTORE READINESS MAP  (created vs. production-wired)
--------------------------------------------------------------------------------
Some stores are CREATED (schema/collection exists, usable) in one phase and only
PRODUCTION-WIRED (at scale, replicated, dashboarded) later. This prevents the
mistake of assuming a store is "done" when only its schema exists.

Store            Created (schema/usable)   Production-wired (scale/replica/DR)
--------------   -----------------------   -----------------------------------
CockroachDB      P00                       P14 (multi-region sync replication)
ScyllaDB (chat)  P08 (RF>=3 AZ)            P14 (cross-region RF, residency)
Memory Postgres  P09                       P14 (cross-region replica)
Qdrant           P09 (memory) / P10 (corpus) P14 (rebuild-from-text DR proven)
FoundationDB     P06                       P14 (replication + Temporal multi-cluster)
OpenSearch       P10                       P14 (index rebuild-from-object-store DR)
Redpanda         P13                       P14 (cross-region replication)
ClickHouse       P12 (tables) / P13 (ingest) P14 (backups + multi-region aggregation)
Object store     P00                       P00 already cross-region-capable; residency in P14
Caches (Redis)   P00                       ephemeral; rebuild-on-demand, no DR needed

DR targets (RPO/RTO) for each class are defined in the architecture DR table and
exercised in Phase-14 drills; this map only tracks WHEN each store reaches that
posture.
