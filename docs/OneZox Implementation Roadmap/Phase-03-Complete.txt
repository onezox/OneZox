PHASE-03 — DATA PLANE FAST PATH — COMPLETION RECORD  [SHIPPABLE MILESTONE M1]
================================================================================
This document records the work actually completed for Phase-03 on the local
onezox-dev Kubernetes cluster (kind, WSL2 Ubuntu 24.04). It contains only
work that was performed and verified. It does not contain Phase-04 work,
future plans, recommendations, or opinions. Phase-03-Progress.txt remains
the point-in-time findings record (drift, process gaps); this document is
the completion summary, in the same style as Phase-00/01/02-Complete.txt.

This phase carries heavier freight than its predecessors: it is the first
phase where three independently-built real services (edge-gateway, data-plane,
provider-gateway) actually chain together into one live request path, and the
first phase to make one real, billed call to a frontier model. Both of those
firsts surfaced a genuine, previously-undetected defect that had been present,
unnoticed, since Phase-01 — see EC4 below, given its own full section rather
than folded into a checklist line.

--------------------------------------------------------------------------------
PHASE-03 OBJECTIVE
--------------------------------------------------------------------------------
Replace the Phase-00/01 dataplane-stub with a real Python data plane: a
complexity classifier that routes simple requests to a template-DAG fast path
(zero LLM planning cost), a minimal scheduler that binds role->model using
live provider health from provider-gateway, streaming fan-in relaying
provider deltas up through the edge, and final metering (real tokens_in/out,
orch_tokens, usd_cost) written to usage_event/request_log. After this phase
the whole vertical slice is real, end to end: edge (P01) -> data plane (P03)
-> provider-gateway (P02) -> a real frontier model -> streamed back to the
user. This is M1 — the first thing a person could actually use.

ones): edge-gateway's DATAPLANE_STUB_ENDPOINT default and dataplane_client

EC4 IN FULL: THE TRACE-PROPAGATION DEFECT
--------------------------------------------------------------------------------
This is recorded as its own section, not a checklist line, because of what
it actually was: a real, silent, cross-cutting defect present in every one
of the three real services since the phase that built each of them, caught
only because this phase was the first to chain three real services together
and the first step in this project's history to ask "is this ONE trace, not
three."

WHAT WAS FOUND: querying Tempo for a real request's trace (initially, EC1's
own real Anthropic call) returned THREE separate trace IDs — one rooted at
edge-gateway, one at data-plane, one at provider-gateway. Each service's own
spans were individually well-formed and genuinely exported to Tempo; that is
precisely why this was never caught. Phase-01's own Step J1 built and
verified edge-gateway's span tree — correctly, within that one service.
Phase-02's own Steps N1-N3 did the same for provider-gateway — also
correctly, within that one service. Neither phase, nor anything before this
step in Phase-03, had ever verified that a trace SURVIVES crossing a service
boundary, because Phase-03 is the first phase where three real services
actually form one live call chain end to end. Phase-01's and Phase-02's own
"telemetry verified" completion claims were TRUE, exactly as scoped — single-
service. They were never true cross-service, because cross-service tracing
did not exist to test until this phase's own cutover (Step J). This is
stated here as an honest correction to those prior records' scope, not as an
error in them: neither phase claimed more than it had, and neither could
have caught this without a second and third real service to chain against.

ROOT CAUSE, identical in shape across all three languages, confirmed
precisely before any fix was written (not assumed): NONE of edge-gateway
(Rust, opentelemetry crate), data-plane (Python, opentelemetry-api/sdk), or
provider-gateway (Go, go.opentelemetry.io/otel) had ever called
set_text_map_propagator. Every OTel SDK except Python's defaults to a
no-op propagator — so even if an inject()/extract() call site had existed
anywhere in the three codebases (it did not, confirmed by grepping every
dependency manifest for a gRPC-context-propagation package), it would have
silently done nothing. The one asymmetry that shaped where explicit
propagator setup was actually required: Python's own
opentelemetry.propagate.get_global_textmap() was confirmed, interactively,
to already return a real CompositePropagator by default — the only one of
the three SDKs that does.

WHY THE FAKE DID NOT PROTECT AGAINST THIS, AND WHY THAT MATTERS BEYOND THIS
ONE BUG: this defect was present in EVERY Submit call made this entire
phase, fake or real, from Step B onward — it has nothing to do with which
provider actually answered the request. It hid because no verification step
before Step L ever queried Tempo for cross-service trace connectivity, not
because the fake behaves differently from a real provider at the tracing
layer (it doesn't participate in tracing at all; provider-gateway's own
spans are identical in shape whether provider-fake or Anthropic answers
underneath them). The real lesson for future phases: a testing regime built
around "validate logic against the fake, spend real calls only on the
functional EC1 proof" is exactly right for functional correctness, and did
its job throughout this phase — but it provides zero coverage of
cross-cutting infrastructure like tracing, which needs its own explicit,
dedicated check (which is precisely what this step's own instructions,
matching P01-J/P02-N's discipline, required and caught).

THE FIX, one coordinated commit across all three services (it only works
once every side of every hop has it):
  - edge-gateway: opentelemetry::global::set_text_map_propagator(...) added
    to init_telemetry(); dataplane_client::submit() now injects the current
    span's context into the outgoing tonic Request's metadata via a small
    MetadataMap Injector adapter.
  - data-plane: Submit() now extracts incoming trace context from
    context.invocation_metadata() BEFORE starting its own root span
    (previously always parentless); scheduler.place.bind_via_provider_health
    and aggregator.relay both inject the active span's context into their
    own outgoing calls to provider-gateway.
  - provider-gateway: otel.SetTextMapPropagator(propagation.TraceContext{})
    added; both Invoke and ProviderHealth now extract incoming context via a
    shared helper. ProviderHealth had NO span of its own at all before this
    — fixed alongside the propagation fix, not left for later, since a
    propagated-but-spanless call would still have been invisible in the
    tree.

VERIFICATION, against a genuine SECOND real Anthropic call — deliberately
not reused from EC1's own trace, because a broken trace cannot prove its own
fix; this second call is recorded honestly as a second real call, not
folded silently into EC1's one-call framing:
  Queried Tempo for the new request_id: ONE trace ID, not three. Fetched the
  full trace and parsed actual parent-span-ID links directly — not merely
  trusted a shared trace ID, which the search API could in principle group
  without genuine nesting underneath it. 15 spans total across all three
  services. edge_gateway.request is the true root; data_plane.submit's
  parent is an edge-gateway span (edge_gateway.submit); provider_gateway.
  invoke AND provider_gateway.provider_health both parent directly under
  data_plane.submit; provider-gateway's own five internal children
  (coalesce/quota/breaker/adapter/stream) nest correctly under provider_
  gateway.invoke. One connected tree, confirmed by the actual parent-span
  IDs recorded on each span, not inferred from grouping.

Logging (data-plane's own success-path log — present, structured, JSON,

PROBLEMS ENCOUNTERED DURING PHASE-03 AND HOW EACH WAS RESOLVED
--------------------------------------------------------------------------------
1. THE TRACE-PROPAGATION DEFECT (Step L) — full account above. The phase's
   most significant finding: no gRPC hop in any of the three services ever
   propagated trace context, since none had ever registered a global
   text-map propagator. Fixed across all three services in one coordinated
   commit; verified with a genuine second real call, by parsing actual
   parent-span IDs.

2. Dockerfile silently never shipped four of data-plane's own modules
   (Step F). Written at Step B (main.py + generated/ only), never updated
   as planner/, scheduler/, working_memory/, request_log/ were each added
   across Steps C-F. Caught because a rebuilt image's manifest hash came
   back byte-identical to the Step B build — none of these modules were
   wired into Submit yet, so the running service never actually needed to
   import them, which is what let this go unnoticed for four steps.
   Resolution: added the missing COPY lines (and every subsequent new
   module's own line, as each was added in later steps); added a
   boot-time verify_modules_present() smoke test as the ongoing safety
   net against the same class of gap recurring silently again.

3. Loki narrow-time-window false-clean result — the SECOND time this exact
   failure mode has hit this project. First: Phase-02's own Step J3
   post-fix re-verification (Phase-02-Complete.txt Problem #4), a genuine
   ingestion gap misread as a possible regression before being root-caused
   to a missing success-path log line. Second: Step L's own leak re-check,
   where a first Loki query for a real request's own log lines returned
   zero results — nearly trusted as a clean "no leak" pass — caught before
   being trusted only because the SAME query, re-run with a wider time
   window, found the real (harmless) log lines it should have found the
   first time. Both incidents: the fix was not "trust an absent result,"
   it was "prove the query can find something real first" — exactly the
   positive-control discipline this project applies to every other
   adversarial check, now shown to matter for the check's own plumbing
   too, not only for the thing being checked.

4. Redis Cluster gossip-state drift (the WSL2-host-restart failure class
   CLAUDE.md's session-start ritual exists for) recurred twice within this
   phase: once during Steps A1-A8's own live verification (a
   DeadlineExceeded traced to stale cached Redis client state in
   provider-gateway's already-running pods, needing both the recovery
   script AND a manual `kubectl rollout restart deployment/provider-gateway`
   — the script alone only nudges dataplane-stub/provider-stub, not
   provider-gateway/provider-fake), and once during Step G (data-plane
   pods hanging silently, not crashing, inside their own Redis Cluster
   client setup — a stuck-not-crashing pod with no further log output
   after a known I/O step is now a recognized first-line suspect for this
   failure class). Both resolved via scripts/recover-redis-cluster.sh.
   This record states two confirmed incidents THIS phase, precisely, from
