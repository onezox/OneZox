PHASE-02 OBJECTIVE
--------------------------------------------------------------------------------
Replace the throwaway Phase-00 provider-stub with a dedicated Go service that
owns all provider concerns: adapters for OpenAI/Anthropic/Google behind one
internal contract, a fleet-wide quota governor (shared Redis counters, not
per-pod), per-provider circuit breakers with typed fallback signaling, request
coalescing, streaming passthrough with backpressure, and prefix-cache handle
passthrough. Called by the data plane over gRPC in the real architecture;
Phase-03 does not exist yet, so a test harness (grpcurl, plus a purpose-built
provider-fake service) drove it directly throughout.

One ordering decision was made before any real credential touched the
service, at the user's explicit direction: security scaffolding had to be
real and verified BEFORE any real provider API key entered a running pod.
Egress default-deny + allow-list was built and verified in BOTH directions
first; only then was the credential Secret created; only then was it mounted;
only then did the mTLS cutover happen; only then did real provider calls run.
This is why the phase's own step lettering (J1 through N3) does not run in a
flat A-Z order — J's sub-steps are interleaved with K3's mTLS cutover by
design, not by accident.

PROVIDER-GATEWAY SERVICE
--------------------------------------------------------------------------------
services/provider-gateway — Go 1.26, google.golang.org/grpc, prometheus/
client_golang, go.opentelemetry.io/otel. 3,433 lines of non-test Go across
main.go plus internal/{adapters,quota,breaker,coalesce,stream}. 42 unit tests
passing across the module (adapters/openai, adapters/anthropic,
adapters/google, adapters/sse, adapters/azure, adapters/bedrock,
adapters/vllm, quota, breaker, coalesce, stream), zero skipped.

internal/adapters: the shared Adapter/Stream/Registry contract (Part G.1),
plus per-provider packages — fake (test harness only), openai (uniform SSE
chunks, Bearer auth), anthropic (named-event SSE, x-api-key +
anthropic-version headers, system-message hoisting), google (Gemini's
?alt=sse streamGenerateContent variant chosen specifically so it could reuse
the same SSE scanner as the other two; contents/parts shape, role mapping,
x-goog-api-key header so the key never lands in a URL any proxy might log),
and three unwired scaffolds (azure, bedrock, vllm). internal/adapters/sse is
a small shared SSE line-scanner used by all three real adapters — the
per-provider JSON payload shape stays in each adapter's own package.
internal/quota: fleet-wide Redis counter governor. internal/breaker:
fleet-wide Redis circuit breaker with a CurrentState reader built for
ProviderHealth. internal/coalesce: in-flight call dedup, per-pod/in-memory by
design (Phase-02.txt lists no coalesce Redis key). internal/stream: the
gRPC-facing relay translating adapter deltas and fallback signals.

Prefix-cache handle passthrough (Part P) is implemented inline as
adapters.Delta.PrefixCacheHandle, carried through relay.Relay to the proto
response, rather than as a separate internal/prefixcache/ package —
Phase-02.txt's own folder structure lists prefixcache/ as a named module;
this is a minor structural deviation from that listing, noted here rather
than left implicit, though the passthrough itself is fully implemented and
verified (Step I1, and visible in every real Invoke response's
prefix_cache_handle field).

InvokeEmbedding and ProviderHealth remain unimplemented (return
codes.Unimplemented via the embedded UnimplementedProviderServiceServer) —
Phase-02.txt's own APIS CREATED section marks these "used from Phase-10" and
"feeds scheduler" respectively, so this is expected non-scope, not a gap
against this phase's four exit criteria.

Database tables: none owned by this phase, per Phase-02.txt's own DATABASE
TABLES REQUIRED section — confirmed, no CockroachDB or MinIO connection
anywhere in the service. Redis keys (ephemeral): provider:{name}:quota:
{window} and provider:{name}:breaker, exactly as specified.

PROBLEMS ENCOUNTERED DURING PHASE-02 AND HOW EACH WAS RESOLVED
--------------------------------------------------------------------------------
1. Circuit breaker (Step F): OpenedAt originally used time.Now().Unix()
   (whole-second truncation), causing sub-second OpenDuration test values to
   always compare as already-elapsed (an Open breaker would immediately
   read back as HalfOpen in any test running faster than 1 second).
   Resolution: switched to UnixMilli() throughout the breaker package.

2. Loki cluster-wide secrets-read RBAC gap (Step J3): see EC3 above for the
   full account. Root cause was a Helm chart default
   (sidecar.rules.enabled: true) enabling a rule-auto-discovery feature
   nothing in this cluster uses; fixed by disabling it, not by hand-patching
   the generated ClusterRole (which would have drifted back on the next
   Helm upgrade). A broader sweep of every other ClusterRole with any
   secrets-read grant (argocd-*, cilium-operator, cockroach-operator-role)
   found all of them to be legitimate, actively-required control-plane
   permissions — left alone, deliberately, not overlooked.

3. Ephemeral debug containers (kubectl debug --target=X) do not
   automatically inherit the target container's volume mounts, specifically
   the projected service-account-token — discovered while first trying to
   test Loki's own RBAC exposure by attaching a debug container and reading
   the token file directly (got "No such file or directory", and a
   subsequent unauthenticated curl's 403 was not a genuine test of Loki's
   permissions at all). Resolution: switched methodology entirely — used
   `kubectl create token loki --duration=10m` to mint a token genuinely
   bound to the ServiceAccount's own RBAC identity, used directly from this
   session's own shell against the cluster's external API server address,
   with no pod involved at all. (`kubectl create token` itself has a
   10-minute minimum duration; a first attempt at 5m was rejected.)

4. A Loki query during Step J3's post-fix re-verification found zero
   results across 15 poll attempts, initially read as a possible ingestion
   regression from the RBAC fix. Root-caused through a chain of checks
   (loki-gateway's own access log showed continuous successful pushes;
   {app="provider-gateway"} was a known label with historical data; the
   specific new-request time window just had nothing) to the real cause:
   provider-gateway's Invoke handler had zero log statements on the success
   path at all — every log call was on an error/control-signal branch. Not
   fixed at the time (this was Step J3, telemetry completeness is Step N);
   verification was redone correctly by triggering an error-path log
   instead, found on the first poll. The success-path gap itself was
   fixed properly at Step N3, and the whole chain — false alarm, root
   cause, deferred fix, actual fix — is recorded across both progress-log
   entries rather than only the final one.

5. Google (Gemini) real-call attempts surfaced a genuine account
   constraint, not a bug: two outdated model-ID guesses 404'd cleanly at
   zero cost; a real response came back but with zero content (the whole
   token budget consumed by internal reasoning under a max_tokens=10 cap);
   a retry timed out at the adapter's own 60s client timeout; a specific
   model (gemini-2.0-flash) returned a clean 429 RESOURCE_EXHAUSTED
   showing generate_content quota=0 on this key's free tier. Every attempt
   reached the real endpoint and returned well-formed JSON (including
   errors), which is what distinguished this from the known TLS-
   intercepting-proxy hazard or an adapter bug. Not fixed — cannot be, from
   code — filed as Dependencies.txt row F13 (see DEFERRALS).

6. Step N1's span design had a non-obvious wrinkle that shaped the
   implementation rather than being a bug caught after the fact:
   coalesce.Group.Invoke (Step G) returns immediately and runs the
   coalescing leader's real work (quota+breaker+adapter) on a goroutine it
   spawns internally, not on the calling goroutine. A span naively wrapping
   the Invoke() call itself would therefore be near-instant and
   structurally wrong. Resolved by creating the quota/breaker/adapter spans
   INSIDE the `call` closure using the same root-anchored context the outer
   function already held, which correctly makes them siblings of
   "coalesce" (both derived from the root span) rather than children of it,
   and propagates correctly across the goroutine boundary — verified in
   Tempo afterward (EC4 above), not just reasoned through.

7. An earlier comment (written during Step K3's provider-stub cleanup, in
   prometheus-values.yaml) claimed provider-gateway "has no /metrics
   endpoint of its own" — imprecise. The HTTP handler
   (mux.Handle("GET /metrics", promhttp.Handler())) existed since Step C1
   and returned 200 the whole time; what was actually missing, discovered
   while building Step N2, was that nothing provider-gateway-specific had
   ever been registered with it — only Go runtime defaults. The comment was
   corrected in place rather than left to mislead a future reader, and the
   provider-gateway scrape target was added to Prometheus's list only once
   there was something real to scrape (Step N2), the same timing precedent
   edge-gateway followed in Phase-01.

8. Recurring "Exit code 144" on backgrounded `kubectl port-forward`
   commands in this sandboxed environment, at least half a dozen times
   across the phase — consistently not a real failure (the underlying
   process either survived or needed a simple, immediate retry). Treated
   throughout as a known environment artifact, same handling established in
   Phase-01.
