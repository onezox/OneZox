PHASE-00 — FOUNDATION — COMPLETION RECORD
================================================================================
This document records the work actually completed for Phase-00 on the local
onezox-dev Kubernetes cluster (kind, WSL2 Ubuntu 24.04). It contains only
work that was performed and verified. It does not contain Phase-01 work,
future plans, recommendations, or opinions.

--------------------------------------------------------------------------------
PHASE-00 OBJECTIVE
--------------------------------------------------------------------------------
Stand up the repository, contracts, infrastructure-as-code, one running cell,
the foundational data stores, and end-to-end telemetry, so that later phases
plug into a reproducible, observable, typed foundation. No user-facing
services were built. Only three throwaway health stubs were built to prove
the toolchain, the service mesh, and telemetry end-to-end.

DATABASE MIGRATIONS
--------------------------------------------------------------------------------
Three idempotent SQL migration files were created under data/migrations/:
  0001_create_schema_migrations.sql — creates schema_migrations
    (migration_id STRING PRIMARY KEY, applied_at TIMESTAMPTZ).
  0002_create_tenants.sql — creates tenants (org_id UUID PRIMARY KEY
    DEFAULT gen_random_uuid(), name STRING NOT NULL, created_at
    TIMESTAMPTZ, status STRING NOT NULL DEFAULT 'active').
  0003_create_health_probe.sql — creates health_probe (probe_id UUID
    PRIMARY KEY DEFAULT gen_random_uuid(), service STRING NOT NULL, ts
    TIMESTAMPTZ).
Each file uses CREATE TABLE IF NOT EXISTS and records its own application
in schema_migrations via INSERT ... ON CONFLICT (migration_id) DO NOTHING.
A run-migrations.sh script applies all three files in order via kubectl
exec and cockroach sql, then runs SHOW TABLES.

All three migrations were executed against the running onezox-crdb
cluster. Idempotency was proven by running the script twice: the second
run reported "already exists, skipping" for each table and "INSERT 0 0"
for each ledger insert. SHOW TABLES confirmed all three tables exist.

REDIS CLUSTER
--------------------------------------------------------------------------------
Deployed via hand-written Kubernetes manifests (not a Helm chart), because
no actively maintained, freely usable official Redis Cluster Helm chart
was available at the time (see PROBLEMS ENCOUNTERED).
platform/operators/redis/redis-cluster.yaml defines a ConfigMap
(cluster-enabled yes), a headless Service (redis-cluster-headless), and a
6-replica StatefulSet using the official redis:8.2.3-alpine image with
emptyDir storage (no persistent volumes, matching the ephemeral-only
requirement). platform/operators/redis/redis-cluster-init-job.yaml is a
Job that waits for all 6 pods to respond to PING and then runs
"redis-cli --cluster create ... --cluster-replicas 1", forming 3 masters
and 3 replicas covering all 16384 hash slots.

Cluster formation was verified via "cluster info" (cluster_state:ok, all
slots assigned) and "cluster nodes". Read/write correctness was verified
by writing and reading namespaced keys across different hash slots, and by
confirming a deliberate CROSSSLOT error when a multi-key command spanned
two slots — proving genuine sharding rather than a single-node fallback.

STUB SERVICES (RUST, PYTHON, GO)
--------------------------------------------------------------------------------
Three throwaway health-check services were built, one per required
language:

edge-stub (services/edge-stub) — Rust, using axum and tokio. Connects to
CockroachDB via tokio-postgres, Redis via a cluster-aware
redis::cluster::ClusterClient, and MinIO via the rust-s3 crate. Emits an
OpenTelemetry trace span over OTLP, exposes Prometheus metrics via the
prometheus crate, and logs structured JSON via tracing and
tracing-subscriber, bridged to OpenTelemetry via tracing-opentelemetry.

dataplane-stub (services/dataplane-stub) — Python, using FastAPI and
uvicorn. Connects to CockroachDB via asyncpg, Redis via
redis.asyncio.cluster.RedisCluster, and MinIO via the official minio
client. Emits an OpenTelemetry trace span, exposes Prometheus metrics via
prometheus-client, and logs structured JSON via a custom logging
formatter.

provider-stub (services/provider-stub) — Go, using the standard library
net/http. Connects to CockroachDB via pgx, Redis via a cluster-aware
redis.NewClusterClient, and MinIO via minio-go. Emits an OpenTelemetry
trace span, exposes Prometheus metrics via client_golang, and logs
structured JSON via the standard library log/slog package.

Each service exposes GET /healthz, GET /readyz (checking CockroachDB and
Redis connectivity), and GET /metrics. On boot, each service writes one
row to health_probe, performs a namespaced Redis SET and GET
({tenant}:{service}:boot), and uploads one test object to the
onezox-artifacts bucket in MinIO.

CILIUM MTLS ENFORCEMENT
--------------------------------------------------------------------------------
Three CiliumNetworkPolicy resources were created
(platform/stubs/mtls/ciliumnetworkpolicy.yaml): edge-stub-mtls,
dataplane-stub-mtls, and provider-stub-mtls. Each policy defines ingress
only rules for its corresponding stub service:
  - traffic from the "host" entity (kubelet health probes) is allowed
    without authentication.
  - traffic from the Prometheus pod (matched by label
    app.kubernetes.io/name=prometheus) is allowed without authentication.
  - traffic from the other two stub services is allowed only with
    authentication.mode: "required".
No egress rules were defined in any of the three policies.

These policies were committed and pushed to the GitHub repository and
applied by syncing the existing "onezox-stubs" Argo CD Application.

The following was verified against the live cluster after the sync:
  - All three CiliumNetworkPolicy resources show VALID: true.
  - Existing pod health, kubelet probe results, and Prometheus scrape
    target health were unchanged before and after the policies were
    applied (0 restarts on all three stub pods; all scrape targets
    remained "up").
  - Requests between each pair of stub services (edge-stub to
    dataplane-stub, edge-stub to provider-stub, dataplane-stub to
    provider-stub) succeeded (HTTP 200) after the policies were applied.
  - A request from a pod matching none of the allowed identities was
    rejected: the client observed a connection timeout, and Cilium's own
    monitor showed the exact events "action deny, auth: disabled, match
    none" followed by "drop (Policy denied)" for that pod's identity.
  - SPIRE's registered entries include a distinct SPIFFE ID for each of
    the three stub services' Cilium identities
    (spiffe://spiffe.cilium/identity/<id>).
  - Cilium's own authenticated-connections table ("cilium-dbg bpf auth
    list") showed authenticated entries with AUTH TYPE "spire" for all
    three pairs of stub services, each with a future expiration
    timestamp.
  - A live capture of a first connection attempt between a previously
    unauthenticated pair showed Cilium's own transition from "action
    deny, auth: spire" (authentication required, not yet established) to
    "action allow, auth: spire" (authentication completed) for the same
    connection.

--------------------------------------------------------------------------------
GITHUB ACTIONS CI (BUF, BUILD, SBOM & SIGNING AUTOMATION)
--------------------------------------------------------------------------------
A single workflow, .github/workflows/ci.yml, was created and committed to
the existing GitHub repository. It triggers on every "push" and every
"pull_request", with no branch or path filters, and defines two jobs.

Job "proto":
  - Installs buf 1.72.0 from the official release binary.
  - Runs "buf lint" against proto/.
  - Runs "buf breaking" against the previous commit (on a push event) or
    the pull request's base commit (on a pull_request event), comparing
    directly against the live GitHub remote via buf's own git-reference
    input syntax. The check is skipped only when there is no prior
    reference to compare against (a brand-new branch with no push
    history).

Job "build-sign" (matrix over edge-stub, dataplane-stub, and
provider-stub, with fail-fast disabled so one language's failure does not
hide the other two's results; depends on the "proto" job succeeding
first). For each of the three services:
  - Builds its Docker image with "docker build --provenance=false
    --sbom=false", which keeps the image a plain single manifest. This
    was a deliberate choice: BuildKit's default OCI attestation manifests
    produce the same multi-manifest shape that had earlier broken
    "kind load docker-image" during local deployment (see PROBLEMS
    ENCOUNTERED, item 13).
  - Installs Syft 1.49.0 from the official install script and generates
    an SPDX-JSON SBOM of the built image, uploaded as a workflow
    artifact.
  - Starts a temporary "registry:2" container inside the job as an
    ephemeral local OCI registry, mirroring the same approach used to
    prove cosign signing in Step 24 — no image is published anywhere
    outside the job. Pushes the built image to it and captures its
    digest.
  - Installs cosign 3.1.2 from the official release binary and signs the
    pushed image digest using the existing development key pair, and the
    existing no-Rekor signing configuration
    (.tooling/cosign/signing_config_no_tlog.json, already tracked in the
    repository from Step 24).
  - Verifies the signature against the already-tracked public key
    (platform/security/cosign/cosign.pub).
  - Removes the ephemeral registry container.

The private signing key and its password are not committed to git — this
matches the existing, already-established Phase-00 policy that
.tooling/cosign/cosign.key and cosign.password stay local-only and
gitignored. To make signing possible in CI without violating that policy,
they were instead stored as encrypted GitHub Actions repository secrets
(COSIGN_KEY and COSIGN_PASSWORD) on the existing onezox/OneZox
repository, sourced from the same local key-pair files, and referenced in
the workflow only as "${{ secrets.COSIGN_KEY }}" /
"${{ secrets.COSIGN_PASSWORD }}".

The workflow file was committed and pushed to the main branch of the
existing GitHub repository, which triggered a real run on GitHub's own
Actions runners. That run was checked directly via the GitHub CLI and
API: all four jobs (proto, and the three build-sign matrix jobs for
edge-stub, dataplane-stub, and provider-stub) completed with conclusion
"success", and all three SBOM artifacts (sbom-edge-stub, sbom-provider-
stub, sbom-dataplane-stub) were confirmed present on the run.

PROBLEMS ENCOUNTERED DURING PHASE-00 AND HOW EACH WAS RESOLVED
--------------------------------------------------------------------------------
1. The first Terraform apply of the kind cluster hung indefinitely because
   wait_for_ready was set to true while the default CNI was disabled, so
   the control-plane could never report Ready. Resolution: the apply was
   stopped, the partially created containers were deleted with
   "kind delete cluster", wait_for_ready was set to false, and the apply
   was re-run, completing in 24 seconds.

2. The Argo CD Helm chart's bundled Redis image could not be pulled: the
   chart's default image registry (an AWS ECR Public mirror) was
   unreachable from this network, confirmed by testing both the mirror
   domain and AWS's canonical ECR Public domain. Resolution: the Redis
   image was overridden to the equivalent Docker Hub image via
   "helm upgrade --set redis.image.repository=redis
   --set redis.image.tag=8.2.3-alpine".

3. buf lint failed with a PACKAGE_DIRECTORY_MATCH violation because the
   initial proto package names included an "onezox." prefix that did not
   match the existing directory layout. Resolution: the prefix was
   removed from all five package declarations.

4. "cargo check" reported an error on the intentionally empty Cargo
   workspace (a workspace with zero members has nothing to check).
   Resolution: "cargo metadata" was used instead to verify the workspace
   file is valid, which is the correct verification method for an empty
   workspace.

5. The CockroachDB Operator crash-looped with "too many open files". The
   first cause identified was that kind's node containers inherited
   Docker's default 1024 soft file-descriptor limit. Resolution: Docker's
   default-ulimits were raised in /etc/docker/daemon.json, which required
   restarting Docker and recreating the onezox-dev cluster (ulimits are
   fixed at container-creation time), after which Cilium and Argo CD were
   reinstalled.

6. After the file-descriptor fix, the same CockroachDB Operator crash-loop
   persisted. The actual cause was identified as
   fs.inotify.max_user_instances, a Linux kernel limit (128) shared across
   the entire host, not per container; the sum of inotify instances in use
   across the host and all three nodes was 123 of 128. Resolution: the
   limit was raised via a sysctl configuration file
   (/etc/sysctl.d/99-onezox-inotify.conf), applied live with no restart
   required, and the crash-looping pod was deleted to force a clean retry.

7. No actively maintained, freely usable official Helm chart for Redis
   Cluster was available: the long-standing default chart's images had
   been moved behind a paid catalog, and the remaining free community
   chart had not been updated in over two years. Resolution: Redis
   Cluster was deployed using hand-written Kubernetes manifests (a
   ConfigMap, headless Service, StatefulSet, and a Job to run
   "redis-cli --cluster create") against the official redis image
   directly.

8. MinIO's server-side encryption was configured (a KMS key was set) but
   was not yet the default for new objects, so a freshly written object
   showed no encryption metadata. Resolution: "mc encrypt set sse-s3" was
   run against each bucket and added to the bucket-initialization Job so
   the fix is reproducible, and a fresh object was confirmed to show
   "Encryption: SSE-S3".

9. Loki's chart defaults to auth_enabled: true, which would have required
   an X-Scope-OrgID header on every request, silently breaking the OTel
   Collector's log exporter and Grafana's Loki data source. Resolution:
   auth_enabled was set to false before this caused a failure.

10. After Tempo was installed, the OpenTelemetry Collector's Tempo
    exporter continued to fail with a gRPC "no children to pick from"
    error even though Tempo was healthy and DNS resolution was confirmed
    working. The cause was a stale, cached negative resolver state in the
    Collector's gRPC client from the period before Tempo existed.
    Resolution: the Collector pod was deleted and allowed to restart,
    establishing a fresh connection.

11. cosign's default signing behavior attempted to upload to the public
    Rekor transparency log, which failed with a TLS certificate error; the
    certificate returned for rekor.sigstore.dev identified itself as
    belonging to an unrelated domain, indicating a TLS-intercepting proxy
    on the network. Resolution: a signing configuration file with the
    Rekor transparency-log URL removed was generated and used, and the
    test image was signed without a transparency-log entry.

12. Copying files into a kind node's /tmp directory via "docker cp"
    completed without error but the file did not appear, because /tmp
    inside the node is mounted as tmpfs with the noexec option, which the
    container runtime silently refused to copy into. Resolution: the
    target path was changed to /root/ inside the node, which succeeded.

13. "kind load docker-image" failed for the locally built stub-service
    images with an error importing a multi-platform manifest, because the
    images were built with Docker Buildx's default attestation manifests
    attached, which kind's importer could not resolve. Resolution: each
    image was saved with "docker save", copied into each node with
    "docker cp", and imported directly with
    "ctr --namespace=k8s.io images import", bypassing kind's own loader.

14. All three stub services crash-looped on first deployment with Redis
    "MOVED" errors, because each service used a plain, non-cluster-aware
    Redis client against the Redis Cluster, and plain clients do not
    follow cluster redirect responses. Resolution: each service was
    changed to use a cluster-aware client
    (redis::cluster::ClusterClient in Rust,
    redis.asyncio.cluster.RedisCluster in Python, and
    redis.NewClusterClient in Go).

15. edge-stub's exported trace did not contain its intended
    "edge_stub.boot" span; instead, unrelated internal spans from the
    gRPC/HTTP2 transport library used by the OTLP exporter appeared in
    Tempo. The cause was holding a synchronous tracing span guard across
    multiple ".await" points, which is documented to break span-context
    propagation for asynchronous code. Resolution: the boot sequence was
    rewritten as its own async function and wrapped with ".instrument()"
    instead of a manual "enter()" guard, and a log-level filter was added
    to reduce unrelated transport-library tracing output. After the fix,
    the correctly named "edge_stub.boot" span was confirmed present in
    Tempo.

16. provider-stub failed at startup with an OpenTelemetry error reporting
    conflicting resource schema URLs, caused by merging the SDK's default
    resource with a resource built against a specific, differently
    versioned semantic-conventions package. Resolution: the merge was
    removed and the resource was built directly from the pinned semantic
    conventions package only.

17. Prometheus was not scraping the three stub services' own /metrics
    endpoints; only the OpenTelemetry Collector was configured as a
    scrape target. Resolution: a second scrape job listing all three stub
    services was added to Prometheus's configuration.

18. No agent was shipping the stub services' container standard-output
    logs into Loki; Loki's ingestion had previously only been proven via
    its OTLP endpoint, not via container log collection. Resolution: a
    Promtail DaemonSet was installed and configured to push to Loki, and
    each stub service's structured JSON logs were confirmed present in
    Loki afterward.

19. When testing traffic between stub pods directly, "kubectl debug"
    initially failed because the pod's own name was passed as the
    "--target" value instead of the container's name inside the pod.
    Resolution: the correct container name was used, after which the
    ephemeral debug container correctly shared the pod's network identity.

20. An initial attempt to observe a denied connection using
    "cilium-dbg monitor -t policy-verdict" filtered to a single endpoint
    ID produced no output for the denied traffic. Resolution: the monitor
    was re-run with both "-t drop" and "-t policy-verdict" and without an
    endpoint filter, which correctly surfaced the "action deny" and
    "drop (Policy denied)" events for the rejected connection.
