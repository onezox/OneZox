2026-08-04 — Steps A1-A8: real token-usage propagation + ProviderHealth,
completing two Phase-02-declared-but-deferred obligations at their first
real consumer
--------------------------------------------------------------------------------
CONTEXT: Phase-03's plan reached Step A (contracts) and found provider-gateway
had no mechanism to carry real token usage at all — Delta had no usage field,
and none of the three real adapters even parsed a usage payload out of their
provider's response (OpenAI: stream_options.include_usage was never set;
Anthropic: message_start was discarded entirely; Google: usageMetadata was
never read). This lines up with Phase-01-Complete.txt and Phase-02-Complete.txt
both already naming real metering as "Phase-03's job" — not a P02 defect, an
expected gap closed at its first real consumer. Separately, ProviderHealth
(declared in Phase-02.txt's own APIS CREATED section) was still Unimplemented
for the same reason: no consumer existed before Phase-03's scheduler.

BOUNDARY HELD (explicit user instruction, worth recording because it shaped
every line of this work): provider-gateway CARRIES and REPORTS usage; it
never ACTS on it. No token-based rate limiting (that's Dependencies.txt F2,
P13), no cost-routing (P12-P14's learned router), no analytics (P13). Confirmed
at the end of Steps A1-A7: no new code path reads InputTokens/OutputTokens for
any decision — only reads and forwards.

A1: provider.proto's Delta gains optional int32 input_tokens/output_tokens.
Presence IS the signal (proto3 optional) — set means a real number, unset
means "not reported," never coerced to zero anywhere downstream. buf lint and
buf breaking both pass clean (purely additive).

A2: internal adapters.Delta mirrors the same two fields; relay.go carries them
through unconditionally when set. CRITICAL design point, per explicit
instruction to check the unhappy path before building it: "final delta only
on the happy path" would create a billing hole — a mid-stream provider
failure after real tokens were already generated would otherwise report
nothing, and a caller could easily (wrongly) read that as zero. Fixed by
having main.go's Invoke handler send ONE best-effort final delta
(finish_reason="error", usage left UNSET) on any relay.UpstreamError, right
before returning the error status — gRPC server-streaming allows sending
messages before the terminating status, so this doesn't require Relay's own
loop to change. The one gap this can't close (there's no live channel left to
send anything through): if the CALLER's own connection to provider-gateway
drops before any final delta arrives at all, there's nothing provider-gateway
can do — that case has to be handled symmetrically at the caller (data-plane's
own Step H metering: "call ended with no final delta" = incomplete, not zero).

A3 (OpenAI): real wire-format subtlety caught here, not assumed — with
stream_options.include_usage, usage arrives in a DEDICATED final chunk (empty
choices, populated usage) that comes AFTER the finish_reason chunk, not on
it. The adapter previously returned IsFinal the instant it saw finish_reason
(old design, per the file's own former header comment) — that would have
skipped the usage chunk entirely. Restructured to defer finish_reason in
stream.pendingFinishReason and keep reading one more chunk; falls back to
returning the deferred finish_reason with usage left unset if [DONE] arrives
without a usage chunk ever showing up (handles a misbehaving response
gracefully rather than losing the finish signal).

A4 (Anthropic): usage is split across TWO different events, not one dedicated
chunk — message_start carries usage.input_tokens (the very first event,
before any content), message_delta carries usage.output_tokens alongside
stop_reason. message_start previously fell into the catch-all "no data
needed" default branch and was silently discarded. Now captured into
stream.inputTokens and reunited with message_delta's output_tokens on the one
final delta. Confirmed input_tokens stays genuinely nil (not 0) if
message_start is somehow never seen.

A5 (Google): simplest of the three — Gemini's usageMetadata is a top-level
chunk field present on every chunk as a running cumulative count, just read
off the same chunk that carries finishReason. Not exercised against the real
API this phase (Dependencies.txt F13 — quota=0 on the available key); verified
against a canned real-shaped payload only, same interim measure F13 already
documents for the rest of this adapter.

A6 (provider-fake): normal/slow modes attach fixed InputTokens=42/
OutputTokens=17 to the final chunk (deterministic, for Step H4's later
metering-math tests). New fail_mid_stream mode: two real content chunks, then
a deliberately truncated JSON fragment, connection closed — simulates a real
provider breaking mid-stream, which is exactly the scenario A2's best-effort-
delta design exists for.

A7 (ProviderHealth): implemented as a pure status READ — quota.Counter gained
Peek (alongside the existing Increment) specifically so checking headroom
never itself consumes any quota; breaker.CurrentState (already built in P02
for exactly this RPC) supplies breaker state. Both fail open on a store error
at the call site (not baked into Headroom's own return value, mirroring how
Enforce already separates its fail-open Decision from its untrustworthy-on-
error current value). adapters.Registry gained Names() so "report on every
known provider" (empty ProviderHealthRequest.provider) reflects whichever
adapters actually registered, not a hardcoded list.

A8 — LIVE VERIFICATION (both services rebuilt, redeployed via onezox-stubs,
confirmed against the running cluster, not just unit tests):

1. Real usage, happy path (fake:normal): final delta carried
   inputTokens=42, outputTokens=17 — exactly matching provider-fake's fixed
   constants, confirming the full chain (fake server -> fake adapter ->
   internal Delta -> relay -> proto Delta -> grpcurl) end-to-end.

2. Real usage, mid-stream failure (fake:fail_mid_stream): FIRST ATTEMPT
   caught a real gap — the fake ADAPTER's own client-side parseMode
   allowlist didn't know "fail_mid_stream" yet (only the fake SERVER, Step
   A6, had been taught the mode), so the request was rejected client-side
   before ever reaching provider-fake. Fixed (parseMode extended), rebuilt,
   redeployed. Retried and got a SECOND, unrelated failure: DeadlineExceeded.
   Root-caused via provider-gateway's own logs to Redis Cluster connection
   timeouts ("dial tcp ... i/o timeout", "cluster has no nodes") — this
   session's host had restarted (silently, without an obvious session
   boundary) since the cluster was last known healthy, the exact
   documented WSL2-restart gossip-state-loss failure mode CLAUDE.md's
   session-start ritual exists for, hit mid-build because that ritual
   wasn't re-run after the restart. Recovered via
   scripts/recover-redis-cluster.sh (cluster_state:fail -> ok, 16384/16384
   slots) plus a manual `kubectl rollout restart deployment/provider-gateway`
   (the script only nudges dataplane-stub/provider-stub, not
   provider-gateway/provider-fake — provider-gateway's own already-running
   pods were holding a Redis client cached against pre-reset node IPs and
   needed a fresh client, not just a healthy cluster to reconnect to).
   THIRD attempt succeeded cleanly: two real content deltas delivered
   ("Hello ", "from ") — confirming already-sent content survives a later
   mid-stream failure — followed by the best-effort final delta
   (finish_reason="error", is_final=true, usage fields genuinely ABSENT,
   not zero), with the underlying RPC error correctly
   Unavailable/"decode chunk: unexpected EOF" (a real error, not a clean
   EOF that would have been misread as success).

3. ProviderHealth: empty request correctly enumerated all 4 registered
   providers (fake, openai, anthropic, google — all three real keys are
   present in this deployment); fake showed breaker=CLOSED,
   quota_headroom=0.983 (reflecting the one real request already made in
   the current window, not a stale/cached value); openai/anthropic/google
   all showed breaker=CLOSED, headroom=1.0 (correct defaults — never
   called this session, fresh window). A provider-scoped request
   correctly filtered to just that one provider's status.

LESSON RECORDED for future sessions in this environment: a silent host
restart (no explicit "new session" signal, just a date rollover noticed
mid-task) can leave Redis Cluster gossip state stale WITHOUT the working
directory or conversation otherwise looking any different — the failure
only surfaced as a mid-build timeout on an otherwise-unrelated test. The
session-start ritual (recover-redis-cluster.sh + confirm cluster_state:ok)
needs to be treated as "run when in doubt," not only literally at the
first message of a conversation.

2026-08-04 — Step B: data-plane skeleton deployed; live verification found
provider-gateway-mtls didn't recognize the new caller identity
--------------------------------------------------------------------------------
Skeleton built: DataplaneService.Submit as a stub (no classifier/DAG/
scheduler — Steps C/D/E), completing the RPC with a clearly-marked
placeholder response rather than a bare UNIMPLEMENTED status, matching
dataplane-stub's own established "stub that completes successfully with
canned content" idiom. Structured logging on the SUCCESS path built in
from the start (both "request received" and "request completed" log
lines) — the exact gap Phase-01 (edge-gateway Step J3) and Phase-02
(provider-gateway Step N3) both had to retrofit.

FINDING: first deploy crashlooped on startup. Boot sequence connects to
CockroachDB (health_probe insert) and Redis (set/get) successfully, then
crashed calling provider-gateway's ProviderHealth RPC — AioRpcError
UNAVAILABLE, "failed to connect to all addresses". Root cause:
provider-gateway-mtls's ingress rule for port 50051 only recognized
app=dataplane-stub as an allowed caller — data-plane's own real Cilium
identity wasn't in the allow-list, so the connection was correctly
blocked by the mesh, not a code bug. This is exactly the relationship
that policy's own comment already anticipated ("Phase-02.txt's own real
caller relationship, data plane -> provider gateway, doesn't arrive
until Phase-03") — Phase-03 had now arrived.

FIX: widened provider-gateway-mtls's port-50051 ingress rule to allow
EITHER dataplane-stub OR data-plane (matchExpressions, In) — a widening,
not a replacement; dataplane-stub keeps its access until Step J's
cutover removes it, same mesh-identity-safe sequencing used throughout
this project (never remove the old identity's access before the new
one is confirmed healthy). Updated the file's stale header/rule comments
to match, rather than leaving them describing a "doesn't arrive until
Phase-03" state that was no longer true.

VERIFIED after the fix: data-plane reached 1/1 Running, full boot
sequence completed (health_probe row written, Redis round-trip
confirmed, provider-gateway ProviderHealth returned all 4 registered
providers with real breaker/quota state). A live Submit call via grpcurl
returned the placeholder response correctly, and BOTH the entry
("request received") and completion ("request completed") structured
log lines appeared — confirming the success-path logging discipline is
genuinely built in, not just present in the code and never exercised.

Preliminary deployment only — no CiliumNetworkPolicy of data-plane's own
yet, no cutover, dataplane-stub still the active service edge-gateway
forwards to. Both arrive at Step J.

2026-08-04 — Step E: scheduler.place proven to genuinely react to live
provider health, all four signal states
--------------------------------------------------------------------------------
The point of this step was never "call ProviderHealth" — it was proving
bind_via_provider_health's decision actually CHANGES based on what that
call returns. A binder that ignores the response looks identical to a
working one exactly as long as the provider stays healthy; the 22 unit
tests committed alongside this step prove the pure decision logic
(bind()) is correct for every input combination, but only a live test
against the real deployed provider-gateway proves the WIRING between the
real RPC response and that decision logic is genuine, not just plausible
in isolation.

METHOD: a standalone script (not wired into Submit — Step E is logic +
live proof only, matching Steps C/D's "no premature wiring" discipline)
imported scheduler.place directly and called bind_via_provider_health
against a port-forwarded, already-deployed provider-gateway, driving the
real "fake" provider's breaker/quota Redis state into each condition
before each call.

1. HEALTHY (breaker closed, full headroom — the state already present):
   BOUND worker_ref='fake:normal'.
2. EXHAUSTED (breaker OPEN): tripped for real via 5 consecutive
   worker_ref=fake:fail Invoke calls through provider-gateway (confirmed
   via a live FALLBACK_REASON_BREAKER_OPEN on the 5th, then via a direct
   Redis read of provider:fake:breaker showing state=open) ->
   REFUSED provider='fake' reason='circuit breaker is open'.
3. DEGRADED (breaker HALF_OPEN): backdated provider:fake:breaker's own
   opened_at past BREAKER_OPEN_DURATION_SECONDS so provider-gateway's
   own effectiveState logic derives half-open — confirmed via a live
   ProviderHealth call showing BREAKER_STATE_HALF_OPEN BEFORE testing
   the binder, so the test is known to be exercising what it claims to
   -> BOUND worker_ref='fake:normal' (the case that actually proves the
   reaction isn't a blunt "refuse anything imperfect": half-open must
   still bind, letting the trial call through, or provider-gateway's own
   breaker could never recover — no trial call would ever reach it).
4. EXHAUSTED (quota): set provider:fake:quota:{current_window_bucket} to
   60 (the default QUOTA_LIMIT_PER_MINUTE). First attempt landed in a
   bucket that expired between the SET and the check (a genuine 60s
   window-boundary race, caught by ProviderHealth's own reported
   headroom, not assumed) — redone against the then-current bucket,
   confirmed via ProviderHealth (quotaHeadroom absent from the JSON,
   which for a proto3 scalar float at exactly 0.0 means zero, not a
   missing/broken field — proto3 JSON omits default-valued fields) ->
   REFUSED provider='fake' reason='fleet-wide quota exhausted'.

All test-induced state reset afterward (breaker forced back to
{"state":"closed","failures":0,"opened_at":0}, the quota key deleted) so
later steps start from a clean "fake" provider, not test debris.

2026-08-04 — Step F: both statelessness halves proven under a real,
hard mid-request pod kill; Dockerfile found to be silently stale
--------------------------------------------------------------------------------
FINDING (caught rebuilding for this test, before any live verification
ran): data-plane's Dockerfile still only copied main.py and generated/ —
written in Step B, before planner/, scheduler/, working_memory/, or
request_log/ existed, and never updated as each was added across Steps
C-F. The rebuilt image's manifest hash came back byte-identical to the
Step B build, which is what surfaced it — none of these modules have
been wired into main.py/Submit yet, so the running service never
actually needed to import them, and this would otherwise have surfaced
as a confusing failure the moment something finally did. Fixed by adding
the four missing COPY lines; confirmed the rebuilt manifest hash actually
changed this time.

METHOD (both halves must pass, testing one is a false pass): from inside
a live, already-deployed data-plane pod (not from the host — Redis
Cluster's multi-shard topology makes host-side port-forward unreliable
for a cluster-aware client, the same reason provider-gateway and
data-plane both got preliminary in-cluster deployments), ran the REAL
working_memory.write()/request_log.write() functions (not a hand-rolled
simulation) to write: a working_memory key (ttl=30s, simulating
"currently in-flight" state) and a request_log row (simulating "a prior,
already-completed request's committed row"). Confirmed both readable.
Then hard-killed that EXACT pod (`kubectl delete pod --grace-period=0
--force` — no graceful shutdown window, matching the "unhappy path, not
clean completion" discipline Phase-01's H3 established) and checked
state at three points, not two, to make the causality unambiguous:

1. Immediately after the write (before the kill): both present.
2. ~1 SECOND after the hard kill (TTL showing 29 of 30 remaining):
   working memory key STILL FULLY PRESENT — proves Redis has zero
   awareness of or dependency on the pod's liveness; the kill itself
   does not and cannot trigger deletion. request_log row also present,
   unaffected (CockroachDB isn't running in the pod that died). A first
   attempt at this exact check used an 8s TTL and the sequential tool
   calls (write, then a separate kill command, then a separate check
   command) took long enough in wall-clock time that the TTL had
   already elapsed naturally by the time of the check — an ambiguous
   result, redone with a 30s TTL specifically to leave an unambiguous
   margin rather than trusting a result that could have been explained
   two different ways.
3. 32 SECONDS after the kill (past the 30s TTL): working memory key
   GONE (TTL command returns -2, "key does not exist" — not 0, not an
   error). request_log row STILL PRESENT, completely unaffected by the
   TTL, which was never a property of that table at all.

A fresh data-plane pod also came up on its own (Deployment's normal
reconciliation) and reached 1/1 Ready without intervention — the service
itself recovers cleanly from a hard kill, not just the data.

Both halves of the boundary this phase's statelessness claim is actually
about are now proven, not assumed: ephemeral state evaporates (via a TTL
that was directly confirmed to be SET, not just intended — the
immediate-after-kill check literally read the countdown), and durable
state persists elsewhere, entirely independent of any specific
data-plane pod's fate.

2026-08-04 — Step G: assembled Submit flow verified live against
provider-fake; caught a stale Redis Cluster (session-start ritual
skipped) and confirmed model source is a deployment-level static ref,
not a per-request override
--------------------------------------------------------------------------------
FINDING 1 (pre-existing, not introduced by Step G): after syncing the
Step G image, both the new and the pre-existing data-plane pods hung
forever right after "wrote health_probe row" and never opened port 8080,
so the liveness probe killed them (exit 137) in an endless CrashLoop.
`redis-cli cluster info` showed cluster_state:fail (5461/16384 slots ok,
10923 pfail) — the WSL2 host-restart gossip-state-drift failure class
CLAUDE.md's session-start ritual exists specifically to catch, and this
session had not run scripts/recover-redis-cluster.sh before starting.
The pod wasn't crashing on a bug; it was blocked inside its own Redis
Cluster client setup, indefinitely, with no timeout — a silent hang, not
a loud failure, which is worth remembering: a stuck-not-crashing pod
with no further log output after a known I/O step is now a first-line
Redis Cluster health suspect. Ran the recovery script (reset the 6
redis-cluster pods, re-ran redis-cluster-init, confirmed 16384/16384
slots ok); it also has a step 6 that nudges any stuck Redis-dependent
stub pods, which threw "provider-stub: no pods found" — a stale
reference to a pod pruned in Phase-02, not a new problem. Deleted the
stuck data-plane pods to force a clean reschedule against the
now-healthy cluster; the fresh pod booted cleanly through every stage,
including the Step G smoke-test line ("boot: all required modules
present: [...aggregator]").

FINDING 2: the Step G task description asked to test fake:slow/fake:fail
via a per-request `worker_ref`, but Phase-03's scheduler binds against
STATIC_MODEL_REF (a Deployment-level env var), and Submit's request.model
field is not consulted — this is the phase's own documented constraint
("Model source is a STATIC ref this phase... do NOT build registry
lookup now"), not an oversight. A grpcurl call with model:"fake:slow"
therefore silently ran against whatever STATIC_MODEL_REF actually was
(fake:normal), returning in 0.07s instead of the expected ~4.2s —
caught by checking timing, not by an error, which is exactly the kind of
false-positive Step C/D's "assert the negative" discipline warns about.
First fix attempt was `kubectl set env deployment/data-plane
STATIC_MODEL_REF=fake:slow` directly against the cluster; Argo CD's
self-heal reverted it within the sync interval (confirmed via `kubectl
get deployment ... -o jsonpath='{...env}'` flipping back to fake:normal
on its own) — a correct enforcement of CLAUDE.md's "never kubectl apply
directly, go through Argo CD" rule, not a bug, and a useful live
confirmation that self-heal is actually wired up. Redone properly: three
sequential git-tracked commits (fake:slow -> fake:fail -> fake:normal),
each pushed and `argocd app sync onezox-stubs`'d before testing, ending
on fake:normal as the lasting state.

METHOD/RESULTS (live, in-cluster, via grpcurl against the pod's Service,
port-forwarded — host-side gRPC works fine here, unlike Redis Cluster's
client-side MOVED-redirect problem):
  - fake:normal: full assembled chain (admit -> classify -> template ->
    working_memory write -> scheduler bind -> aggregator relay ->
    working_memory delete) produced the correct 6-chunk stream plus a
    final is_final=true/finish_reason="stop" message, and both the
    "request received" and "request completed
    latency_ms=..." structured log lines appeared — the
    integration proof AND, since this is the first Submit call to
    actually execute classifier/templates/scheduler/working_memory/
    aggregator inside the running pod, the image-completeness proof
    Step F's Dockerfile bug motivated adding verify_modules_present()
    for.
  - fake:slow: 6 chunks at 700ms apiece streamed through the full chain
    (provider-fake -> provider-gateway -> data-plane -> grpcurl client)
    with measured wall-clock elapsed=4.28s, matching 6x700ms — confirms
    no buffering/batching anywhere in the relay path collapses the
    delay, i.e. backpressure genuinely holds end-to-end rather than the
    provider-gateway or data-plane draining the upstream stream early
    into memory.
  - fake:fail: provider-fake returns HTTP 503 with no streaming at all;
    provider-gateway's adapter (Step A2's "error-path best-effort
    delta") surfaces one best-effort Delta with finish_reason="error"
    before the stream terminates with a genuine grpc.RpcError
    (UNAVAILABLE); aggregator.relay() yields that delta normally, then
    the next iteration raises ProviderStreamError, which Submit converts
    to a clean `context.abort(UNAVAILABLE, ...)` — the client-visible
    result is one partial message followed by a single well-formed
    UNAVAILABLE status (grpcurl's own "ERROR: Code: Unavailable" block),
    not a raw transport failure or a hang. The pod's own "provider
    stream error ..." WARNING log line appeared. Confirmed the `finally:
    await admit.release(...)` held on this error path too: read
    `admission:data-plane:inflight` from Redis directly after the call
    and got 0, not a leaked count.

Both of Step G's Dockerfile-completeness and backpressure/error-path
claims are now proven live, not just unit-tested; the Redis Cluster
incident is the fourth time this exact failure class has surfaced this
build (see A1-A8's entry) and reinforces that the session-start ritual
is not optional even mid-phase.
