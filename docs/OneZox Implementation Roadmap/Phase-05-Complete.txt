       onezox-canary-481c5d68-...-95fa9c75  stage=canary_1   value [0]

EC2. AN INDUCED REGRESSION TRIGGERS AUTOMATIC ROLLBACK.
     MET — and met on the REAL elevated-error signal, distinguishable from the
     empty-data and Inconclusive fail-safes.

     Rollout 28f39753-e4d3-4e84-b6d8-db4e86f29a37. A manifest version was

     failure mode — zero cost, zero risk, 100% reliable), then canaried under

     THE DISTINGUISHING EVIDENCE — this is what separates "EC2 proven" from

       message: 'Metric "canary-error-rate" assessed Failed due to

     Connected AS the admin_api role (not root, which bypasses GRANTs):
       UPDATE audit_log SET action='tampered' WHERE audit_id=189fdc9a-...
         -> ERROR: user admin_api does not have UPDATE privilege on relation
            audit_log   SQLSTATE 42501

EC4. NO PATH EXISTS TO MUTATE A LIVE MODEL OUTSIDE SIGNED MANIFESTS + ROLLOUT.
     MET — proven adversarially at all three layers a bypass could hide in
     (Step T), on top of four structural properties that make most of the
     surface unrepresentable rather than merely refused.

     LAYER 1 — DATABASE. Connected as the admin_api role:
       SELECT * FROM model_manifest              -> 42501 (no SELECT privilege)
       UPDATE model_manifest SET status=...      -> 42501
       DELETE FROM model_manifest WHERE ...      -> 42501
       UPDATE model_active SET active_version_id -> 42501  (flip the live
                                                            pointer directly)
       UPDATE rollout SET stage='stable',
              status='promoted'                  -> 42501  (jump to 100%)
     All five refused. Note the BARE SELECT is refused too: admin_api has zero
     grants on these tables, not merely restricted ones. State re-read after
     the attempts and confirmed unchanged (active_version_id still
     0290afa3-..., manifest status still published, rollout still
     canary_1/rolled_back).

     LAYER 2 — NETWORK. A throwaway pod with no matching Cilium identity was
     created in the default namespace and attempted to reach control-plane:
       nc control-plane.default.svc.cluster.local 50051  -> hung to timeout
       nc control-plane.default.svc.cluster.local 8080   -> hung to timeout
     POSITIVE CONTROL, from the SAME pod in the same session:
       nc prometheus-server.default.svc.cluster.local 80 -> "succeeded!"
     This is what proves the hangs are Cilium's default-deny silently
     dropping, and not general network breakage or a bad DNS resolution.

     LAYER 3 — API PARAMETER. Crafted requests attempting to skip staging:
       CreateRollout   {..., "canary_percent":100, "target_stage":"stable"}
         -> message type control.v1.CreateRolloutRequest has no known field
            named canary_percent
       PromoteRollout  {..., "target_stage":"stable", "new_percent":100}
         -> message type admin.v1.PromoteRolloutRequest has no known field
            named target_stage
       StartRollout    {..., "initial_percent":100}
         -> message type admin.v1.StartRolloutRequest has no known field
            named initial_percent
     The request could not even be CONSTRUCTED. This is stronger than a
     server-side rejection: there is no field to send, so there is nothing for
     a validation check to have to catch.

     STRUCTURAL ENFORCEMENTS (why the above is a floor, not the whole story):
       - NO BYPASS VERB. Neither admin.proto nor control.proto defines an RPC
         that sets model_active directly, nor an "instant activate". A verb
         that does not exist cannot be invoked by any caller, however
         privileged.
       - PARAMETERLESS PROMOTE. PromoteRolloutRequest carries only rollout_id.
         Stage progression comes exclusively from control-plane's fixed
         internal stageOrder slice; the next stage is computed, never
         supplied. Unit-tested, and confirmed by reading advanceStage.
       - TYPE-LEVEL READ/WRITE SPLIT. graph.controlReader (U1b) has no
         RegisterModelManifest/CreateRollout/PromoteRollout/AbortRollout
         method, so a GraphQL resolver cannot invoke a mutation — it will not
         compile. Same for providerHealthReader (one method), so admin-api
         structurally cannot originate provider traffic via Invoke.
       - NETWORK-UNREACHABLE AUTOMATIC PATH. The reconciler is a plain
         goroutine with no listener of any kind. There is no port to reach it
         on, so no network policy is even required to protect it.
       - PANEL HAS NO DIRECT ACCESS. admin-panel has no database client, no
         Vault client and no etcd client. Every action goes through admin-api.
       - ADMIN-API HAS NO VAULT OR ETCD CLIENT either — it cannot sign or
         publish a manifest even if its own RBAC were bypassed.

--------------------------------------------------------------------------------
CROSS-PHASE TOUCH — THE PHASE-04 ACTIVATION FIX (STEP H)
--------------------------------------------------------------------------------
Recorded explicitly because it modifies a Phase-04 service, and this phase was
chartered as a consumer of Phase-04.

WHAT CHANGED. control-plane's RegisterModelManifest previously activated every
newly-registered manifest version unconditionally. That was correct for
Phase-04, where registration was the only way a version came into existence and
there was no other mechanism to make one live. It is wrong the moment a canary
system exists: publishing a new version would have instantly redirected 100% of
live traffic to it, which is precisely the outage class this entire phase
exists to eliminate — and would have made EC1, EC2 and EC4 unprovable.

The fix makes activation CONDITIONAL: a manifest for a model_ref with no
active version yet still bootstraps (first-ever version must become live, or
nothing could ever serve), but a model_ref that already has an active version
is published INERT, awaiting a rollout. Extracted as
registry.Service.ActivateVersion, which is now the single "make this version
live" path shared by the bootstrap branch and rollout's own promotion
transition — one implementation, two callers.

WHAT DID NOT CHANGE, and was re-verified afterward:
  - Manifest immutability. model_manifest is still INSERT-only at the DB role
    level; nothing about the immutability grant was touched.
  - Vault Transit signing. Every version is still signed on write, with the
    identical signed_payload construction.
  - Independent verification. data-plane and edge-gateway still verify every
    manifest themselves; unchanged code, re-confirmed live at Step P when both
    services re-verified all six openai versions after a restart.
  - The etcd distribution path and the PublishActive envelope shape.

HONEST FRAMING. This is not a Phase-04 defect that went unnoticed. Phase-04
had no consumer that could distinguish "publish" from "activate", so the two
were legitimately fused; the seam only becomes visible when the first consumer
that needs them separated arrives. It IS, however, a real change to a
previously-completed phase's service, made in this phase, and is recorded as
such rather than folded silently into Step H.

SECURITY INCIDENT — ADMIN TOKEN PRINTED TO TRANSCRIPT (STEP U2)
--------------------------------------------------------------------------------
WHAT HAPPENED. While verifying the panel's login flow, the full HTTP response
headers of a successful Server Action POST were printed, including:

  set-cookie: onezox_admin_session=<RAW ADMIN TOKEN>; Path=/; Secure;
              HttpOnly; SameSite=strict

The intent was to verify the three cookie ATTRIBUTES (Secure, HttpOnly,
SameSite). The attributes were the only thing that needed to be observed. The
credential value was printed alongside them because the whole header was
echoed rather than filtered.

DISCLOSURE AND CONTAINMENT. Disclosed immediately and unprompted in the same
turn it occurred. Both credentials seeded for that test (the admin and the
viewer of org phase05-panel-test) were revoked within the same turn via
admin_user.revoked_at.

PROVEN DEAD, not merely assumed revoked:
  leaked token -> admin-api GraphQL       HTTP 401
  leaked token -> panel session cookie    307 -> /login
Both re-tested after revocation. The revocation path itself is therefore also
now live-verified, which it had not been before this incident.

BLAST RADIUS: nil. The org (phase05-panel-test) was created solely for this
verification, held no data, and both of its credentials are revoked. No
production or long-lived credential was involved.

THIS IS THE THIRD CREDENTIAL-INTO-TRANSCRIPT INCIDENT in this build:
  1. Phase-04: `kubectl get secret -o yaml` printed base64-encoded provider
     keys (base64 is encoding, not encryption).
  2. Phase-04: grpcurl against IssueProviderToken printed the full response,
     including the Vault-issued token.
  3. Phase-05 (this): curl printed the full Set-Cookie header, including the
     admin session token.

ROOT CAUSE IS CONSISTENT ACROSS ALL THREE, and it is not carelessness about
what is sensitive — in every case the sensitivity was known and the rule was
known. The pattern is: verification printed a WHOLE RESPONSE when only a
SHAPE or an ATTRIBUTE needed checking. CLAUDE.md's rule ("verify field NAMES /
response SHAPE only") is correct and was understood each time; it failed three
times because it is enforced by discipline at the exact moment attention is on
something else (here: reverse-engineering an unfamiliar wire format, after
several failed attempts). See the first TRACKED FINDING for the structural fix
this warrants.

--------------------------------------------------------------------------------
TRACKED FINDINGS (CARRIED FORWARD — NOT DONE THIS PHASE)
--------------------------------------------------------------------------------
1. LEAK-SAFE VERIFICATION HELPER — highest-value hardening available.
   "Assert credential attributes, never print the value" has now failed three
   times on discipline (see SECURITY INCIDENT). Every other invariant of
   comparable importance in this system has been made STRUCTURAL rather than
   procedural, and each time that conversion is what actually held:
     - `import 'server-only'`      -> a Client Component importing the session
                                      module is a BUILD failure, not a review
                                      catch.
     - parameterless PromoteRollout -> a stage jump is unrepresentable, not
                                      merely rejected.
     - controlReader as a type      -> a resolver mutation will not compile.
     - GRANT-based immutability     -> the database refuses, not the app.
   The equivalent here is a small verification helper that takes a response
   and a list of expected attributes and prints ONLY pass/fail per attribute,
   with no code path that can emit the underlying value. This is the one
   remaining leak class in this build still resting on discipline rather than
   structure, and the three-strike record is the argument for converting it.

2. AUDIT CHOKEPOINT FOR SUCCESS/FAILURE.
   Current state is HYBRID, and the two halves differ in strength:
     - DENIAL audit is CHOKEPOINT-enforced (authz.UnaryInterceptor runs on
       every gRPC call before any handler body) and, as of Step R, unit-tested
       across all six methods. A future RPC is covered automatically.
     - SUCCESS/FAILURE audit is HAND-WIRED per handler. It works — Step R
       verified all six exhaustively — but it is REINTRODUCIBLE: a future
       mutating RPC could ship with a handler that omits audit.Write and
       nothing would fail at compile time. The CreateApiKey gap found in Step R
       is not hypothetical evidence for this; it is an instance of it.
   Harden to a response-side interceptor or codegen check so all audit
   coverage is unskippable by construction, matching denial.

3. BOOT-TIME REGISTRATION RETRY — RECURRING (hit twice).
   Services that fail their boot-time Vault/manifest registration fail CLOSED
   and stay broken permanently, with no automatic retry. The fail-closed
   behaviour is CORRECT and should not change. What is missing is recovery:
   a service that booted during a transient Vault/DNS outage remains dead
   until a human restarts it, even after the dependency is healthy again.
     - Phase-04 Step U: first occurrence.
     - Phase-05 Step P: data-plane booted during a WSL2-restart DNS/Vault
       window and marked all six openai manifests permanently untrusted;
       provider-gateway booted in the same window and registered ZERO provider
       adapters. Both required a manual `kubectl rollout restart`. This was
       discovered only because it broke a live proof.
   Should be retry-with-backoff so the service self-recovers when the
   dependency returns. Tracked as a resilience-hardening item, not a
   correctness defect.

4. STATEFUL-LAYER GITOPS ADOPTION — deferred to a cloud phase.
   The observability stack is now Argo CD-managed with self-heal proven (see
   PROBLEMS #2). The stateful layer — CockroachDB, etcd, Redis, MinIO, Vault,
   plus argo-rollouts — remains manually managed. Deferred deliberately:
   adopting them requires a per-component drift check and a backup/restore
   story first, because a values mismatch there risks data loss or Raft
   corruption rather than a briefly-wrong dashboard. To be done per-component,
   with backups, in a cloud phase.

5. ADMIN-PANEL EXPOSES NO /metrics.
   Every backend service in this fleet exposes Prometheus metrics; the panel
   does not. Named here rather than papered over — panel request metrics would
   be a real addition, and adding an empty endpoint purely for consistency
   would be worse than the honest gap. Its CiliumNetworkPolicy correspondingly
   has no Prometheus ingress rule.

6. CARRIED DEFERRALS FROM EARLIER PHASES, still open and unchanged:
   F13 (Gemini, suspended), F2 (KEDA -> P13), provider-gateway HPA,
   usd_cost wiring (-> P06), Redis working-memory isolation model

PROBLEMS ENCOUNTERED AND RESOLVED
--------------------------------------------------------------------------------
1. RECONCILER STALLED FOREVER ON "Inconclusive" (Step O, live-caught).
   With this project's own count:1 AnalysisRun spec, Inconclusive is Argo
   Rollouts' TERMINAL verdict — status.completedAt is already set and the
   object never re-evaluates. The reconciler grouped Inconclusive with
   Pending/Running ("still waiting"), so a rollout that hit a 0/0 NaN once was
   orphaned at that stage permanently. Fixed: Inconclusive now shares
   AutoRollback with Failed/Error — an ambiguous SLO verdict must not promote
   an unvetted canary to more live traffic, and must not hang either. Same
   fail-safe discipline as the consecutiveErrorLimit fix from Step M.
   (2bc126e, b9e88a6)

2. NO GRACE PERIOD BEFORE THE FIRST EVALUATION (Step O, live-caught).
   The reconciler created a stage's AnalysisRun immediately on entering the
   stage, and Argo evaluated it within ~1 second — structurally before any
   canary-labelled request could have been recorded. Every stage's query was
   therefore a deterministic 0/0 (NaN), for every rollout, healthy or not.
   Not a flaky timing issue: a race the reconciler always lost.
   Fixed by adding rollout.stage_entered_at (migration 0021) and a 30s
   stageGracePeriod checked before CreateForStage. DB-persisted rather than an
   in-memory timer, so it survives a control-plane restart mid-canary exactly
   like every other piece of rollout state. Without this fix EC1 was
   unprovable. (98fb5a6, d68e5bb)

3. PROMETHEUS SCRAPE-TARGET DRIFT — live cluster vs git (Step N).
   data_plane_submit_total was emitted correctly but invisible to Prometheus.
   The live scrape config still listed `dataplane-stub` — a service removed
   back in Phase-03 Step J — and never listed `data-plane` at all.
   IMMEDIATE FIX: `helm upgrade prometheus -f prometheus-values.yaml`, after
   which all four onezox targets reported up.
   ROOT CAUSE, which is the more important finding: platform/operators/ was
   OUTSIDE Argo CD entirely. Only platform/stubs/ had a reconciler. The values
   file had been correct in git since Phase-03; nothing ever compared it to the
   live Helm release, so the drift persisted silently for months and was found
   only by accident while verifying a different thing.
   PERMANENT FIX: six Argo CD Applications (prometheus, grafana, loki, tempo,
   promtail, otel-collector) adopting the existing releases via multi-source
   (remote chart + this repo's values via $values, helm.releaseName pinned for
   adoption). Every diff was inspected with `argocd app diff` BEFORE enabling
   automated sync: five were clean no-ops (only Argo's own additive tracking-id
   annotation); tempo showed one inert extra key traced to an
   argocd-repo-server Helm v3.19.4 vs local v4.2.3 template-rendering
   difference, accepted as a single safe restart of a MinIO-backed collector.
   SELF-HEAL PROVEN, not assumed: the live ConfigMap was hand-edited back to
   the exact `dataplane-stub` drift that caused the original incident. Argo
   reverted it in under 30 seconds, with `initiatedBy: {automated: true}` in
   the operation history.
   POSITIVE CONTROL: a legitimate git change (adding admin-api's own /metrics
   as a scrape target — an endpoint that existed since Step E but was never
   wired) synced through normally and was confirmed `up` in Prometheus's
   targets API. Self-heal that also blocked real changes would be a different
   kind of broken. (3c01c49, 8738ef3)
   SCOPE NOTE ON PRIOR CLAIMS: Phase-03-Complete.txt states dataplane-stub's
   "Prometheus scrape target" was confirmed gone. That claim was TRUE and
   remains true — it was about the stub's target being removed from the
   committed values file. It never claimed data-plane's own target was being
   scraped, and no prior phase's telemetry claim depended on it. No earlier
   completion record requires correction.

4. admin_api COULD NOT INSERT INTO api_keys (Step S, live-caught).
   CreateApiKey failed with "user admin_api does not have SELECT privilege on
   relation tenants (SQLSTATE 42501)". api_keys.org_id REFERENCES tenants, and
   CockroachDB/Postgres FK enforcement requires SELECT on the REFERENCED table
   to validate the constraint — not merely INSERT on the table being written.
   Fixed by migration 0022 (GRANT SELECT ON tenants TO admin_api). Read-only,
   and it touches none of the model_manifest/model_active/policy/pricing
   tables EC4's DB-layer proof depends on. (e5c8f95)

5. STRING[] COLUMN WOULD NOT SCAN (Step S, live-caught).
   listApiKeys failed with "unsupported Scan, storing driver.Value type string
   into type *[]string". pgx/v5's database/sql driver returns an array
   column's raw value before Scan knows the destination Go type, so a bare
   *[]string destination cannot decode it. Fixed with pgtype.Map.SQLScanner,
   pgx's own documented workaround. api_keys.scopes is this project's first
   STRING[] read. (4b1f263)

6. CreateApiKey AUDIT GAP (Step R) — see EC3(a). Found by the exhaustive
   sweep, not by a test failure, which is the point of doing the sweep by
   reading every exit path rather than trusting existing coverage.

7. ADMIN TOKEN PRINTED TO TRANSCRIPT (Step U2) — see SECURITY INCIDENT.

8. runAsNonRoot REJECTED THE PANEL'S NAMED USER (Step V).
   The first admin-panel rollout failed with CreateContainerConfigError:
   "container has runAsNonRoot and image has non-numeric user (node), cannot
   verify user is non-root". kubelet cannot verify a NAMED user against
   runAsNonRoot. Fixed with an explicit numeric runAsUser: 1000. (676b338)

9. TRANSIENT ISSUES, recurring and not treated as defects: CockroachDB
   "remote wall time is too far ahead" clock-skew errors (a known WSL2
   artifact, always resolved by a short retry — the reconciler's own error
   handling tolerates them by design), and stale kubectl port-forwards after
   pod rollovers.
