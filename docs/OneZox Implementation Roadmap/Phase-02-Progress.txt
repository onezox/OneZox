2026-08-02 — Step H2: mid-stream disconnect cleanup is bounded, not
immediate — a deliberate trade-off, confirmed live, not a leak
--------------------------------------------------------------------------------
FINDING: Phase-01's edge-gateway (Rust) freed its admission-guard resource
immediately on a mid-stream client disconnect (Step H3, Phase-01). Testing
the same scenario for provider-gateway (Go) found different, but correct,
behavior: killing a client mid-stream against a slow (fake:slow, 700ms/chunk)
call left go_goroutines elevated (12 baseline -> 18 immediately after kill),
only returning to baseline (11) after ~8 seconds — roughly the time the
abandoned call's remaining chunks would have taken to arrive naturally.

This is NOT a leak. It is the direct, intended consequence of Step G's
coalescing design: the leader's context is deliberately stripped of
cancellation (context.WithoutCancel) before the shared quota+breaker+adapter
call runs, specifically so that if the caller who happened to trigger the
call disconnects, the underlying call keeps running for the sake of any
other subscriber (follower) that joined it — a follower's own request must
not be silently aborted just because the leader walked away. The
consequence is that cleanup after a disconnect is bounded by the call's own
natural duration, not immediate.

Verified live against the real deployed service: baseline goroutine count
was re-confirmed identical (11) well after the settle window, ruling out
drift/leak across the test rather than just a single before/after snapshot.

DECISION: left as-is. Phase-02.txt does not specify disconnect-cleanup
timing, and immediate-abort-on-disconnect would directly conflict with
Step G's own coalescing requirement ("a follower riding an in-flight call
[must not be] independently... for work it isn't causing" — aborting the
shared call on ANY one subscriber's disconnect would break every other
still-attached subscriber). If this bound ever needs tightening (e.g. an
explicit max-abandoned-call lifetime, independent of coalescing), that's a
future decision, not a Phase-02 gap — Phase-02.txt's own resilience testing
requirements are about breaker/quota/coalescing/fan-out, not disconnect
latency.

2026-08-02 — Step J3: credential-isolation check found (and fixed) a real
cross-service secret-read path, unrelated to anything Phase-02 built
--------------------------------------------------------------------------------
FINDING: verifying "provider-gateway-credentials mounted only to
provider-gateway" per Phase-02.txt's own SECURITY IMPLEMENTATION wording
was treated as two separate questions, not one: (1) does any OTHER pod's
spec reference this Secret (a mount check), and (2) could any OTHER pod's
service account read it via the K8s API regardless of mounting (an RBAC
check). (1) was clean from the start — scanned all 59 pods across every
namespace, exactly one (provider-gateway itself) references it.

(2) was not clean. loki-clusterrole (installed by Phase-00's Loki Helm
chart — nothing Phase-02 touched) grants get/watch/list on `secrets`
AND `configmaps`, cluster-wide, completely unscoped. Confirmed this was
genuinely exploitable, not just a theoretical rule: minted a token bound
to the `loki` ServiceAccount (`kubectl create token loki`) and used it to
fetch provider-gateway-credentials directly from the K8s API — succeeded,
HTTP 200, with all three real provider API key field names present in the
response. Four running pods share this ServiceAccount:
loki-0, loki-chunks-cache-0, loki-gateway, loki-results-cache-0.

ROOT CAUSE: the grafana/loki chart's templates/backend/clusterrole.yaml
gates its entire rules list behind a single values flag,
`sidecar.rules.enabled` (chart default: true) — true grants the blanket
configmaps/secrets access shown above (needed only for the chart's
rule-auto-discovery sidecar, which loads Loki alerting/recording rules
from labeled ConfigMaps/Secrets); false renders `rules: []`. Nothing in
this cluster stores Loki rules that way, so the feature was already dead
weight — not a capability anything here actually used.

FIX: set `sidecar.rules.enabled: false` in
platform/operators/loki/loki-values.yaml (committed, then applied via
`helm upgrade` directly — platform/operators/ isn't in the "onezox-stubs"
Argo Application's watched path, same established exception Prometheus's
own config already uses per Phase-01 Step F3b). Confirmed via `helm
template` before applying that this produces `rules: []` and removes the
now-pointless kiwigrid/k8s-sidecar container entirely, not just the RBAC
grant. Re-verified post-apply: the same loki-scoped token that got HTTP
200 before now gets HTTP 403 ("... is forbidden: User
\"system:serviceaccount:default:loki\" cannot get resource \"secrets\"").

VERIFIED LOKI ITSELF STILL WORKS after the fix, not just that the
permission was removed: loki-0 rolled out cleanly (1/1 Ready); a fresh
real request through provider-gateway's error path produced a log line
found in Loki within one poll, both via Loki's own query API and through
Grafana's proxied datasource query — ingestion and querying both intact.

SEPARATE FINDING, surfaced by accident while chasing what first looked
like a Loki regression: provider-gateway's Invoke handler has NO log
line at all on a successful request (main.go only calls log.Warn/
log.Error on error paths) — the exact same gap Phase-01's edge-gateway
had before its own Step J3 fixed it. A request that completes cleanly
currently produces zero structured-log output. Not fixed here — this is
Step N's job (EC4 telemetry completeness), noted so it doesn't get
rediscovered as a surprise then.

RESIDUAL, NOT ACTIONABLE: a broader sweep of every ClusterRole for any
remaining secrets-read grant turned up argocd-application-controller,
argocd-server, argocd-notifications-controller, cilium-operator, and
cockroach-operator-role, plus the built-in (unbound-by-default) `admin`/
`edit` templates. All are legitimate, actively-required control-plane/
operator permissions (Argo CD's own GitOps engine needs broad secret
access to function at all; Cilium's operator manages its own mTLS
certs; CockroachDB's operator manages CRDB's own TLS rotation) — nothing
here is idle capability the way Loki's sidecar grant was, and narrowing
any of them risks breaking core cluster function well outside Phase-02's
scope. Left as-is, deliberately, not overlooked.

2026-08-03 — Step K3: mTLS cutover from provider-stub to provider-gateway,
mesh-identity-safe sequencing confirmed both halves
--------------------------------------------------------------------------------
Two-commit cutover, same pattern Phase-01 Step F2 used for edge-gateway:

(1/2, commit 33ab9b6): added provider-gateway-mtls (ingress-only, mirrors
dataplane-stub-mtls/edge-gateway-mtls's host+Prometheus no-auth rules, plus
one SPIRE-authenticated rule for dataplane-stub -> provider-gateway on
50051) and synced it BEFORE touching provider-stub at all. Verified
VALID:true, Cilium endpoint for provider-gateway flipped Disabled->Enabled
on ingress. Live proof: a raw socket connection from dataplane-stub to
provider-gateway:50051 produced a fresh `cilium-dbg bpf auth list` entry
(SRC 47734 = provider-gateway, DST 63524 = dataplane-stub, AUTH TYPE spire,
EXPIRATION ~51 min in the future at check time) — genuinely SPIRE-issued,
not stale/cached.

(2/2, commit 0786836): only once (1) was confirmed healthy — removed
provider-stub-mtls entirely, the stale provider-stub rule from
dataplane-stub-mtls, and provider-stub from edge-gateway-mtls's
matchExpressions; deleted platform/stubs/provider-stub/deployment.yaml and
services/provider-stub/ outright; dropped provider-stub from go.work, the
CI build-sign matrix (replaced with provider-gateway), and Prometheus's
onezox-stubs scrape job (applied via `helm upgrade` directly, same
operator-config exception as Loki/Step J3 and Phase-01 F3b). At no point
was provider-gateway deployed without its own mTLS policy in place — no
mesh-identity gap.

NOTE, deliberately NOT carried forward: the old stub pair
(dataplane-stub<->provider-stub) was bidirectional test-capability proof
(both directions on port 8080, neither backed by real RPC logic).
provider-gateway-mtls only recreates ONE direction (dataplane-stub ->
provider-gateway, on 50051, the real gRPC port) — the reverse direction
was not recreated since provider-gateway has no reason to call
dataplane-stub and inventing that relationship would be scope beyond
Phase-02.txt. One proven direction is sufficient to demonstrate the SPIRE
mTLS capability.

VERIFIED POST-CUTOVER: `kubectl get deployment,svc,pods -l app=provider-stub`
returns nothing; onezox-stubs Argo app Synced/Healthy; remaining 3
CiliumNetworkPolicies (dataplane-stub-mtls, edge-gateway-mtls,
provider-gateway-mtls) all VALID:true; live Prometheus target list
(`/api/v1/targets`) shows provider-stub gone and no premature
provider-gateway entry (it still has no /metrics endpoint — that's Step
N); a real streamed Invoke call through provider-gateway against
provider-fake (fake:normal) succeeded end-to-end after the old identity
was fully removed, confirming the cutover didn't regress functionality.
