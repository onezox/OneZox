2026-08-02 — Step H2: mid-stream disconnect cleanup is bounded, not
immediate — a deliberate trade-off, confirmed live, not a leak
--------------------------------------------------------------------------------
FINDING: Phase-01's edge-gateway (Rust) freed its admission-guard resource
immediately on a mid-stream client disconnect (Step H3, Phase-01). Testing
the same scenario for provider-gateway (Go) found different, but correct,
behavior: killing a client mid-stream against a slow (fake:slow, 700ms/chunk)
call left go_goroutines elevated (12 baseline -> 18 immediately after kill),
only returning to baseline (11) after ~8 seconds — roughly the time the
abandoned call's remaining chunks would have taken to arrive naturally.

This is NOT a leak. It is the direct, intended consequence of Step G's
coalescing design: the leader's context is deliberately stripped of
cancellation (context.WithoutCancel) before the shared quota+breaker+adapter
call runs, specifically so that if the caller who happened to trigger the
call disconnects, the underlying call keeps running for the sake of any
other subscriber (follower) that joined it — a follower's own request must
not be silently aborted just because the leader walked away. The
consequence is that cleanup after a disconnect is bounded by the call's own
natural duration, not immediate.

Verified live against the real deployed service: baseline goroutine count
was re-confirmed identical (11) well after the settle window, ruling out
drift/leak across the test rather than just a single before/after snapshot.

DECISION: left as-is. Phase-02.txt does not specify disconnect-cleanup
timing, and immediate-abort-on-disconnect would directly conflict with
Step G's own coalescing requirement ("a follower riding an in-flight call
[must not be] independently... for work it isn't causing" — aborting the
shared call on ANY one subscriber's disconnect would break every other
still-attached subscriber). If this bound ever needs tightening (e.g. an
explicit max-abandoned-call lifetime, independent of coalescing), that's a
future decision, not a Phase-02 gap — Phase-02.txt's own resilience testing
requirements are about breaker/quota/coalescing/fan-out, not disconnect
latency.

2026-08-02 — Step J3: credential-isolation check found (and fixed) a real
cross-service secret-read path, unrelated to anything Phase-02 built
--------------------------------------------------------------------------------
FINDING: verifying "provider-gateway-credentials mounted only to
provider-gateway" per Phase-02.txt's own SECURITY IMPLEMENTATION wording
was treated as two separate questions, not one: (1) does any OTHER pod's
spec reference this Secret (a mount check), and (2) could any OTHER pod's
service account read it via the K8s API regardless of mounting (an RBAC
check). (1) was clean from the start — scanned all 59 pods across every
namespace, exactly one (provider-gateway itself) references it.

(2) was not clean. loki-clusterrole (installed by Phase-00's Loki Helm
chart — nothing Phase-02 touched) grants get/watch/list on `secrets`
AND `configmaps`, cluster-wide, completely unscoped. Confirmed this was
genuinely exploitable, not just a theoretical rule: minted a token bound
to the `loki` ServiceAccount (`kubectl create token loki`) and used it to
fetch provider-gateway-credentials directly from the K8s API — succeeded,
HTTP 200, with all three real provider API key field names present in the
response. Four running pods share this ServiceAccount:
loki-0, loki-chunks-cache-0, loki-gateway, loki-results-cache-0.

ROOT CAUSE: the grafana/loki chart's templates/backend/clusterrole.yaml
gates its entire rules list behind a single values flag,
`sidecar.rules.enabled` (chart default: true) — true grants the blanket
configmaps/secrets access shown above (needed only for the chart's
rule-auto-discovery sidecar, which loads Loki alerting/recording rules
from labeled ConfigMaps/Secrets); false renders `rules: []`. Nothing in
this cluster stores Loki rules that way, so the feature was already dead
weight — not a capability anything here actually used.

FIX: set `sidecar.rules.enabled: false` in
platform/operators/loki/loki-values.yaml (committed, then applied via
`helm upgrade` directly — platform/operators/ isn't in the "onezox-stubs"
Argo Application's watched path, same established exception Prometheus's
own config already uses per Phase-01 Step F3b). Confirmed via `helm
template` before applying that this produces `rules: []` and removes the
now-pointless kiwigrid/k8s-sidecar container entirely, not just the RBAC
grant. Re-verified post-apply: the same loki-scoped token that got HTTP
200 before now gets HTTP 403 ("... is forbidden: User
\"system:serviceaccount:default:loki\" cannot get resource \"secrets\"").

VERIFIED LOKI ITSELF STILL WORKS after the fix, not just that the
permission was removed: loki-0 rolled out cleanly (1/1 Ready); a fresh
real request through provider-gateway's error path produced a log line
found in Loki within one poll, both via Loki's own query API and through
Grafana's proxied datasource query — ingestion and querying both intact.

SEPARATE FINDING, surfaced by accident while chasing what first looked
like a Loki regression: provider-gateway's Invoke handler has NO log
line at all on a successful request (main.go only calls log.Warn/
log.Error on error paths) — the exact same gap Phase-01's edge-gateway
had before its own Step J3 fixed it. A request that completes cleanly
currently produces zero structured-log output. Not fixed here — this is
Step N's job (EC4 telemetry completeness), noted so it doesn't get
rediscovered as a surprise then.

RESIDUAL, NOT ACTIONABLE: a broader sweep of every ClusterRole for any
remaining secrets-read grant turned up argocd-application-controller,
argocd-server, argocd-notifications-controller, cilium-operator, and
cockroach-operator-role, plus the built-in (unbound-by-default) `admin`/
`edit` templates. All are legitimate, actively-required control-plane/
operator permissions (Argo CD's own GitOps engine needs broad secret
access to function at all; Cilium's operator manages its own mTLS
certs; CockroachDB's operator manages CRDB's own TLS rotation) — nothing
here is idle capability the way Loki's sidecar grant was, and narrowing
any of them risks breaking core cluster function well outside Phase-02's
scope. Left as-is, deliberately, not overlooked.

2026-08-03 — Steps J4-J6: real adapters built + one real call each; EC1 met
2/3, Google content-delta path deferred (Dependencies.txt F13)
--------------------------------------------------------------------------------
Prerequisite finding: only the fake adapter existed going into this step
(Step D1) — the registry had no openai/anthropic/google entries at all.
Building the three real adapters (internal/adapters/{openai,anthropic,
google}, plus a small shared internal/adapters/sse SSE-framing helper)
WAS this step, not a preamble to it — matches Phase-02.txt's own
COMPLETION CHECKLIST item and FOLDER STRUCTURE
(adapters/{openai,anthropic,google,azure,bedrock,vllm}). Each adapter
unit-tested against a canned, real-shaped SSE payload before any real
call was made (httptest.Server, no network, no cost) — caught wire-format
and normalization issues (role mapping, system-message hoisting for
Anthropic/Google, [DONE]-sentinel handling for OpenAI) cheaply, ahead of
spending real provider calls. All pass; full module builds/vets/tests
clean.

REAL-CALL RESULTS:

OpenAI (gpt-4o-mini): full success. Content streamed as three deltas
("ack"+"now"+"ledged" -> "acknowledged"), then finish_reason="stop",
is_final=true. Uniform SSE-chunk wire format parsed correctly end-to-end,
adapter -> relay -> caller.

Anthropic (claude-haiku-4-5-20251001, after an outdated first model ID
404'd cleanly with no cost): full success. Single content delta
"acknowledged", then finish_reason="end_turn" (from the message_delta
event), is_final=true. Named-event SSE stream (message_start /
content_block_delta / message_delta / message_stop) parsed correctly.

Google (Gemini): PARTIAL, not a code defect. Sequence of attempts:
1. Two outdated model IDs (gemini-1.5-flash, gemini-2.5-flash) -> clean
   404s, zero cost, confirmed reachability/auth fine.
2. gemini-flash-latest, max_tokens=10 -> a genuine real response,
   correctly parsed (finish_reason="MAX_TOKENS", is_final=true) but ZERO
   content — the model's whole token budget was consumed by internal
   reasoning before any visible output. This proved the finish-signal SSE
   parse path against the real API but never exercised the content-delta
   path (candidates[].content.parts[].text).
3. Retried with max_tokens=50 on the same model -> 60s client timeout
   awaiting response headers.
4. gemini-2.0-flash -> clean 429 RESOURCE_EXHAUSTED: "Quota exceeded ...
   limit: 0 ... generate_content_free_tier_requests". This key's Google
   Cloud project has NO generate_content quota on the free tier. Every
   attempt in this sequence reached the real endpoint and returned
   well-formed JSON (including the errors) — ruled out the known
   TLS-intercepting-proxy hazard and any adapter bug; this is an
   account/billing constraint, not a wire-format or infra problem.

Confirmed via `kubectl logs`: no key value ever appears in any log line
across this entire sequence, only presence/absence and upstream error
bodies — the "never logged" requirement held throughout, including
through five failed/partial real-call attempts.

DECISION (per explicit instruction): do not chase further Google model
names against a confirmed 0-quota project. EC1 is recorded as MET for
OpenAI and Anthropic, PARTIALLY MET for Google — the content-delta parse
path is a genuine, tracked open item, not silently accepted as "done."
Filed as Dependencies.txt Forward-Reference Tracker row F13: defined P02,
finalized in the cloud phase (first real Gemini content call once a
billed/paid-tier key exists), interim measure is the unit test against a
canned payload, explicit risk noted (a real Gemini dialect difference in
the content-delta shape would not be caught by that unit test or by
provider-fake). Also noted in CLAUDE.md's Phase-02 scoping/deferrals list
so it surfaces immediately in a fresh session, not just in this file.
MUST be carried into Phase-02's own completion record (Step O1) as an
explicit DEFERRALS entry, same pattern Phase-01-Complete.txt used for the
external-ingress deferral — not yet written since O1 hasn't happened.

2026-08-03 — Steps L1-L2: adversarial security tests, positive-controlled,
against the fully-hardened real-key-bearing deployment
--------------------------------------------------------------------------------
Both tests follow the same discipline Phase-01's H1 established: prove the
detection method CAN catch a real positive before trusting a clean/
negative result on it.

L1 — credential-leak test.
Positive control: planted a fake secret-shaped value
("sk-FAKE-positive-control-leak-...") in a JSON line matching
provider-gateway's own slog.JSONHandler shape, confirmed grep finds it —
proves the methodology itself works before trusting an "absent" result.
Real test: exec'd into the running provider-gateway pod, read all three
real key values (OPENAI_API_KEY, ANTHROPIC_API_KEY, GOOGLE_API_KEY) into
shell variables via `kubectl exec ... printenv` — never echoed, only
their lengths were ever printed. Grepped two independent sources
client-side (never sent the key value itself in any query, to avoid
creating a NEW leak surface in Loki's own access log): (1) the pod's full
kubectl logs since last restart (14 lines, covering every real-provider
call made in Steps J4-J6 including all five Google attempts), and (2)
Loki's durable store via /loki/api/v1/query_range for {app=
"provider-gateway"} over the last 2 hours (25 lines). Checked the bare
key value AND "Bearer <key>" (OpenAI's actual header form). All six
checks (3 keys x 2 sources, plus the Bearer-form recheck): zero matches.
Consistent with the source-level finding already established (Step J4-J6
commit message): no adapter package contains a single log/slog call, and
apiKey is an unexported struct field only ever used to set an HTTP
header, never marshaled or logged.

L2 — egress-block test, re-run against the CURRENT state (real key
mounted, mTLS cutover complete, provider-stub fully removed) rather than
relying on the original J1/J2 build-time result.
Positive control: from an ephemeral debug container (nicolaka/netshoot)
sharing provider-gateway's network namespace, curl to
https://api.openai.com/v1/models succeeded (HTTP 401 — a deliberately
wrong bearer token, the point was TCP+TLS+DNS all working, not auth) in
~99ms. Proves the egress policy is actually being evaluated, not
blanket-blocking everything by accident.
Negative test: curl to https://example.com/ timed out. Confirmed this
was a genuine Cilium policy enforcement, not an unrelated network hiccup,
by capturing a live `cilium-dbg monitor -t drop` event on
provider-gateway's node during the attempt: "drop (Policy denied) ...
identity 47734->world: 10.244.1.41:xxxxx -> {172.66.147.243,
104.20.23.154}:443 tcp SYN" — identity 47734 is provider-gateway's own
Cilium identity (same one captured in the K3 mTLS proof), "world" is
everything outside the allow-list, both example.com's resolved IPs were
dropped at the kernel/BPF level (bpf_lxc.c:1651), not just timed out at
the application layer.

RESULT: EC3 (credential isolation and egress allow-list) verified with
adversarial, positive-controlled evidence, not passive confirmation —
same H1 discipline Phase-01 established, applied here against the real,
fully-hardened Phase-02 deployment.

2026-08-03 — Step M1: fleet-wide quota cap proven under real multi-replica
concurrency (EC2)
--------------------------------------------------------------------------------
The E1-E2 quota tests (unit + single-pod live) never actually
distinguished a fleet-wide cap from a per-pod one — both look identical
at replicas=1. M1 required proving it against real concurrency across
multiple pods, since only that setup can expose a per-pod-counter bug.

SETUP: provider-gateway scaled 1 -> 3 replicas; QUOTA_LIMIT_PER_MINUTE
temporarily set to 30 (test-only convenience value, no real-world basis
— reverted after the test, replicas left at 3).

METHOD: port-forwarded to each of the 3 running pods individually
(bypassing the Service's load-balanced ClusterIP, so the split across
pods is explicit and known rather than approximate) and fired 60
concurrent requests, 20 per pod, all within one 60s quota window
(aligned to a fresh window boundary before starting). Each request used
distinct message content (a per-request nonce) specifically to avoid
Step G's own request coalescing — coalescing dedupes by
worker_ref+messages+params, and 60 identical-content concurrent calls
would have collapsed into a handful of actual quota-consuming calls,
invalidating the test. worker_ref: fake:normal (provider-fake, not a
real provider — this is load testing, not adapter verification).

RESULT: 60/60 requests completed. Exactly 30 got a real Delta response
(allowed), exactly 30 got FALLBACK_REASON_QUOTA_EXHAUSTED (throttled) —
the configured cap exactly, not 90 (3x the cap, what a per-pod-local
counter would have produced: each pod only received 20 requests, well
under a hypothetical per-pod 30 limit, so a broken per-pod
implementation would have shown 60/60 allowed with zero fallbacks).
Per-pod breakdown (pod1: 9 allowed/11 throttled, pod2: 13/7, pod3: 8/12)
is itself further evidence: a genuinely shared, contended counter
produces exactly this kind of uneven, race-order-dependent split;
independent per-pod budgets would not.

CONFIRMED DIRECTLY AGAINST REDIS (not inferred from application
behavior alone): exactly ONE key existed for the window
(provider:fake:quota:29762330) — not three separate keys, one per pod.
Its value was exactly 60, matching the total request count across all
three pods combined. TTL was mid-countdown (31s remaining of the fixed
60s window), confirming the fixed-window design is also working as
intended. This is the literal mechanism-level proof that all three
replicas increment the same shared counter, not the application-level
outcome alone.

Positive-control requirement satisfied as part of the same run: the cap
WAS reachably hit (not a limit set so high it never engaged), and every
one of the 30 over-cap requests received the correctly-typed fallback
signal (FALLBACK_REASON_QUOTA_EXHAUSTED), not a generic error.

EC2 (fan-out cap) is now verified fleet-wide under real multi-replica
concurrency, not just single-pod.
